This software repository provides a framework for building and orchestrating multi-agent Large Language Model (LLM) workflows. It enables agents to collaborate, utilize external tools, manage conversational context, and operate reliably.

An [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) combines an LLM with specific instructions, external tools, and validation mechanisms. A [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) executes an agent's tasks, orchestrating interactions with the LLM, tool calls, and transitions between agents. See [Agent Definition and Orchestration](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-agent-definition-and-orchestration).

Agents extend their capabilities by integrating [`tools`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tools.md?plain=1#L1). The Model Context Protocol ( [`MCP`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L1)) standardizes how these tools are exposed and utilized by LLMs. See [Integrating Tools and Model Context Protocol (MCP)](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-integrating-tools-and-model-context-protocol-mcp).

[`Guardrails`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L1) provide validation mechanisms for both user inputs and agent outputs, ensuring adherence to specified safety and operational constraints. See [Guardrails for Robust Agent Behavior](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-guardrails-for-robust-agent-behavior).

Multi-agent collaboration occurs through [`Handoffs`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/handoffs.md?plain=1#L1), enabling agents to delegate tasks to specialized counterparts. This facilitates the construction of complex, distributed workflows. See [Handoffs and Multi-Agent Collaboration Patterns](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-handoffs-and-multi-agent-collaboration-patterns).

[`Sessions`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/sessions/index.md?plain=1#L1) manage conversational context and history across interactions. This ensures agents maintain continuity and coherence throughout a dialogue. See [Agent Memory and Session Management](https://codewiki.google/github.com/openai/openai-agents-python#agent-memory-and-session-management).

[`Tracing`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L159) functionality captures events and execution steps, offering insight into an agent's decision-making process and overall workflow. See [Tracing and Debugging Agent Workflows](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-tracing-and-debugging-agent-workflows).

The framework supports various LLM providers, including OpenAI and other models via LiteLLM. This allows for flexible model selection and configuration within agent applications. See [Model Integration and Configuration](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration).

The framework supports building real-time and voice-enabled AI agents. These capabilities enable low-latency conversational flows and integration with telephony platforms or web applications. See [Real-time and Voice-Enabled Agents](https://codewiki.google/github.com/openai/openai-agents-python#real-time-and-voice-enabled-agents).

## Multi-Agent LLM Workflow Framework

link

zoom\_in

The Multi-Agent LLM Workflow Framework provides a system for constructing AI applications that involve the orchestration of multiple Large Language Models (LLMs) and tools. It defines core components and processes for agents to collaborate, manage conversational context, and ensure the reliability of their operations.

The framework is centered on the concept of an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133), which is an LLM configured with specific instructions, tools, and guardrails to perform tasks. Agent execution is managed by a [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294), which orchestrates the interaction between the LLM, external tools, and other agents. This orchestration involves processing responses from the LLM, executing necessary tool calls, and managing transitions between different agents within a workflow. The agent's operations are further controlled by [`ModelSettings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L59), which allow for fine-tuning LLM parameters and behaviors, including specifying how tools are chosen and utilized.

A key aspect of this framework is its robust system for managing conversation history, known as [`Sessions`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/sessions/index.md?plain=1#L1). These sessions enable agents to maintain context across multiple interactions, facilitating coherent and continuous dialogues. Various session implementations are available, supporting different storage needs and advanced features such as branching and encryption. For detailed information on how conversation history is managed, refer to [Agent Memory and Session Management](https://codewiki.google/github.com/openai/openai-agents-python#agent-memory-and-session-management).

The framework integrates [`tools`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tools.md?plain=1#L1) to extend an agent's capabilities beyond its core LLM functions. These tools can range from hosted utilities like web search and code interpreters to custom functions defined by developers. A specialized mechanism, the Model Context Protocol (MCP), standardizes how tools are exposed to LLMs, allowing agents to discover and utilize them effectively. The integration of tools is further elaborated in [Integrating Tools and Model Context Protocol (MCP)](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-integrating-tools-and-model-context-protocol-mcp).

To ensure that agent behaviors remain within defined boundaries, the framework incorporates [`Guardrails`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L1). These mechanisms validate both user inputs and agent outputs, helping to maintain safety, compliance, and controlled execution of workflows. Guardrails can trigger a halt in execution if predefined conditions are not met, preventing undesirable outcomes. More information on this can be found in [Guardrails for Robust Agent Behavior](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-guardrails-for-robust-agent-behavior).

Multi-agent collaboration is facilitated through [`Handoffs`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/handoffs.md?plain=1#L1), which allow agents to delegate tasks to other specialized agents. This enables the construction of complex workflows where different agents contribute to a larger objective, passing control and relevant context as needed. This topic is covered in depth in [Handoffs and Multi-Agent Collaboration Patterns](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-handoffs-and-multi-agent-collaboration-patterns).

For observability and debugging, the framework includes [`Tracing`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L159) functionality. This system captures events and execution steps, providing insights into an agent's decision-making process and overall workflow. It assists in monitoring, debugging, and optimizing the performance of multi-agent systems. Further details are available in [Tracing and Debugging Agent Workflows](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-tracing-and-debugging-agent-workflows).

The framework also provides comprehensive support for integrating various LLM providers, including both OpenAI and non-OpenAI models. This is achieved through flexible configuration options and integration with tools like LiteLLM, which broadens the range of compatible models. Details on model integration can be found in [Model Integration and Configuration](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration).

For developers looking for practical applications and advanced patterns, the [`examples`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/examples.md?plain=1#L1) directory ( [`examples`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples)) provides a collection of demonstrations, including customer service agents, financial research bots, and real-time voice interactions. These examples illustrate how the core components of the framework can be combined to build sophisticated AI applications. See [AI Agent Examples and Patterns](https://codewiki.google/github.com/openai/openai-agents-python#ai-agent-examples-and-patterns) for more information.

### Agent Definition and Orchestration

link

zoom\_in

The framework for building multi-agent Large Language Model (LLM) workflows is centered around the concept of an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) and its execution managed by a [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294). The [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) class, defined in [`src/agents/agent.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py), represents an LLM configured with specific attributes to perform tasks. These attributes include a [`name`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L216) for identification, [`instructions`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L146) to guide its behavior, and a set of [`tools`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tools.md?plain=1#L1) it can use to extend its capabilities. Agents can also be configured with [`guardrails`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L1) to ensure outputs adhere to specified criteria and [`handoffs`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/handoffs.md?plain=1#L1) to delegate tasks to other agents.

Agent execution is orchestrated by the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) class, which handles the lifecycle of an agent's interaction. The [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) initiates an agent's turn by sending the current conversation history and user input to the LLM. It then processes the LLM's response, which can involve several actions:

- **Executing Tool Calls**: If the LLM's response includes calls to tools, the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) executes these tools. Tools allow agents to interact with external systems, perform computations, or retrieve information. Tools can range from hosted services like web search or file search to custom Python functions or even other agents acting as tools. More details on how agents interact with tools can be found in [Integrating Tools and Model Context Protocol (MCP)](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-integrating-tools-and-model-context-protocol-mcp).
- **Managing Handoffs**: The [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) facilitates the transfer of control between agents using [`handoffs`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/handoffs.md?plain=1#L1). When an agent determines that another agent is better suited to handle a particular task or query, it can trigger a [`handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L86). This mechanism allows for sophisticated multi-agent workflows where specialized agents collaborate to solve complex problems. [Handoffs and Multi-Agent Collaboration Patterns](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-handoffs-and-multi-agent-collaboration-patterns) provides a deeper dive into this concept.
- **Applying Guardrails**: Before an agent's output is finalized or input is processed, [`guardrails`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L1) are applied by the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294). These mechanisms, defined in [`src/agents/guardrail.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py), validate both user inputs and agent outputs, ensuring that interactions remain within defined safety and compliance boundaries. If a guardrail is triggered, the execution might be halted. For more information, refer to [Guardrails for Robust Agent Behavior](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-guardrails-for-robust-agent-behavior).
- **Generating Final Output**: The agent execution loop continues until the LLM produces a [`final_output`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L47) that does not involve tool calls or handoffs. The [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) then delivers this output as the result of the agent's task.

The [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) supports various execution modes, including synchronous ( [`Runner.run_sync`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L56)), asynchronous ( [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92)), and streamed ( [`Runner.run_streamed`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L69)) execution, providing flexibility for different application requirements. The entire process of an agent's execution, including LLM calls, tool executions, and handoffs, is automatically traced, allowing for monitoring and debugging of complex workflows. [Tracing and Debugging Agent Workflows](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-tracing-and-debugging-agent-workflows) covers this in detail.

### Integrating Tools and Model Context Protocol (MCP)

link

zoom\_in

Agents within the framework can extend their capabilities by interacting with external tools. These interactions are managed through various mechanisms, from predefined hosted tools and custom Python functions to agents serving as tools themselves. The Model Context Protocol (MCP) further standardizes how these tools are exposed to Large Language Models (LLMs), allowing for consistent tool discovery and execution across different environments.

Agents can utilize several types of tools:

- **Hosted Tools**: These are predefined tools that provide common functionalities, such as [`WebSearchTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L221), [`FileSearchTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L195), [`ComputerTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L241) for automated web interaction, [`CodeInterpreterTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L323) for executing code, and [`ImageGenerationTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L335). The [`HostedMCPTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L302) facilitates integration with external services that implement the MCP.
- **Custom Function Tools**: Developers can define custom functions in Python and expose them as tools to an agent using the [`@function_tool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L109) decorator or by instantiating the [`FunctionTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L146) class. These functions can be synchronous or asynchronous and allow agents to perform application-specific logic. For example, a [`get_weather`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/basic/tools.py#L16) function could be exposed to an agent to retrieve weather information.
- **Agents as Tools**: An advanced pattern allows an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) instance to be used as a tool by another agent via the [`agent.as_tool()`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/tests/test_agent_as_tool.py#L30) method. This enables hierarchical agent architectures where one agent delegates complex sub-tasks to specialized agents. This is useful for orchestrating multi-agent systems where an overarching agent dispatches tasks to other agents. See [Advanced Agent Design Patterns](https://codewiki.google/github.com/openai/openai-agents-python#ai-agent-examples-and-patterns-advanced-agent-design-patterns) for more examples.

The framework provides mechanisms to control tool interaction, such as [`tool_use_behavior`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L208) and [`tool_choice`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L81) in [`ModelSettings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L59), which allow for fine-grained control over when and how agents use specific tools. Tools can also have [`input_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L202) and [`output_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L284) to validate their inputs and outputs, respectively.

### Model Context Protocol (MCP)

The Model Context Protocol (MCP) is a mechanism for standardizing the exposure of tools and context to LLMs. It defines how a server can offer tools and dynamic prompts to an LLM, allowing the LLM to discover and invoke these capabilities. The MCP is implemented in the directory [`src/agents/mcp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp).

Key aspects of MCP implementation include:

- **Server Implementations**: The framework provides several server implementations for MCP, designed for different communication paradigms:

  - [`MCPServerStdio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L387): For communication over standard I/O streams.
  - [`MCPServerSse`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L489): For Server-Sent Events (SSE), enabling push-based communication from the server to the client.
  - [`MCPServerStreamableHttp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L596): For HTTP-based communication that supports streaming.
    These servers manage the lifecycle of connections, cache tool lists, and handle prompt retrieval.
- **Tool Filtering**: MCP servers support robust tool filtering, which can be static or dynamic.

  - [`ToolFilterStatic`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py#L66) allows tools to be filtered based on [`allowed_tool_names`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L263) or [`blocked_tool_names`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L267).
  - [`ToolFilterCallable`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py#L54) provides dynamic filtering using a callable function that evaluates whether a tool should be exposed based on runtime context, such as the current [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) or [`run_context`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L59).
- **Integration with Agents SDK**: The [`MCPUtil`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py#L109) class in [`src/agents/mcp/util.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py) facilitates the integration of MCP tools with the Agents SDK. It aggregates [`FunctionTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L146) s from multiple [`MCPServer`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L32) instances and converts [`MCPTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/tests/mcp/helpers.py#L6) definitions into the SDK's [`FunctionTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L146) format. When an MCP tool is invoked by an agent, [`invoke_mcp_tool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py#L182) handles the communication with the respective [`MCPServer`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L32), processes the results, and manages errors.
- **Dynamic Prompts**: MCP also supports dynamic prompt generation, where the server can provide prompts to the LLM that are generated at runtime, adapting to the current context or available tools.

Examples of MCP usage can be found in [`examples/mcp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp), demonstrating interactions with local filesystems, Git repositories, and dynamic prompt servers. Further details on model integration are provided in [Model Integration and Configuration](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration).

### Guardrails for Robust Agent Behavior

link

zoom\_in

Guardrails provide mechanisms to ensure that an agent's behavior adheres to specified safety, compliance, and operational constraints. This framework implements both [`InputGuardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L72) and [`OutputGuardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L134) mechanisms, allowing for validation of messages entering an agent and results exiting an agent. These guardrails can be configured to halt execution if certain conditions are met, a process referred to as "tripwire-triggered."

The core of guardrail functionality is defined in [`src/agents/guardrail.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py). An [`InputGuardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L72) can execute either concurrently with the agent's processing or sequentially before it begins, providing flexibility for different validation needs. An [`OutputGuardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L134) performs checks on the final output generated by the agent. When a guardrail function indicates that its [`tripwire_triggered`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L709) flag is [`True`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L69), the agent's operation is immediately stopped, preventing undesirable or unsafe outcomes.

Guardrails are defined using decorators, [`@input_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L75) and [`@output_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/guardrails.md?plain=1#L133), which simplify their creation from standard Python functions. This approach allows developers to integrate custom validation logic directly into their agent definitions. Examples demonstrating the application of these guardrails, including scenarios for streaming operations, can be found in the [`examples/agent_patterns`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns) directory. For more general information on configuring and using guardrails, refer to the [Guardrails](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-guardrails-for-robust-agent-behavior) documentation.

### Tracing and Debugging Agent Workflows

link

zoom\_in

The framework incorporates built-in [`Tracing`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L159) functionality to monitor, debug, and optimize multi-agent workflows. This system captures significant events during agent execution as [`Traces`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tracing.md?plain=1#L14) and [`Spans`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tracing.md?plain=1#L16). These captured events provide a chronological record of the agent's decision-making process, tool interactions, and handoffs, which is crucial for understanding complex behaviors and identifying performance bottlenecks.

Configuration options allow for controlling the logging of sensitive data within these traces. For example, environment variables like [`OPENAI_AGENTS_DONT_LOG_MODEL_DATA`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L87) and [`OPENAI_AGENTS_DONT_LOG_TOOL_DATA`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L93) (managed in [`src/agents/_debug.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/_debug.py)) can be used to prevent model and tool data from being logged, ensuring that confidential information is not inadvertently exposed in debugging outputs. This control helps maintain data privacy and security while still enabling comprehensive debugging. The [`Tracing`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L159) mechanism is designed to provide observability into the agent's internal state and execution flow, allowing developers to track how agents respond to inputs, utilize tools, and delegate tasks within a workflow. This enhances the ability to diagnose issues, refine agent instructions, and improve overall system reliability.

### Handoffs and Multi-Agent Collaboration Patterns

link

zoom\_in

Agent handoffs facilitate task delegation and multi-agent orchestration by allowing one agent to transfer control to another, enhancing the ability to manage complex workflows and specialized tasks. The framework provides the [`Handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L86) class, defined in [`src/agents/handoffs/__init__.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py), which includes mechanisms for structuring input data ( [`HandoffInputData`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L42)), applying message filters, and invoking the target agent.

Handoffs are implemented as specialized tools that agents can invoke. When an agent determines that another agent is better suited to handle a task, it can initiate a handoff. This process involves the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) class, which orchestrates the execution, processes LLM responses, and manages the switch to the new agent when a handoff is triggered. For more details on the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) class, refer to [Agent Definition and Orchestration](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-agent-definition-and-orchestration).

Custom callbacks are supported through the [`on_invoke_handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/tests/test_soft_cancel.py#L390) parameter within the [`Handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L86) definition, allowing for custom logic to be executed when a handoff occurs. This enables flexible integration with various agent types and custom handling of the transfer process.

Managing conversation history during inter-agent transfers is critical for maintaining context. The framework provides [`nest_handoff_history`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/history.py#L61), defined in [`src/agents/handoffs/history.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/history.py), which processes [`HandoffInputData`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L42) to create a new instance with a summarized input history. This summarization prevents redundant nesting and ensures that only relevant context is passed to the next agent. Message filtering can be customized using [`input_filter`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L113) within the [`Handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L86) configuration. For example, the [`remove_all_tools`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/handoff_filters.py#L27) utility in [`src/agents/extensions/handoff_filters.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/handoff_filters.py) can remove tool-related messages from the [`HandoffInputData`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L42), ensuring that only conversational context is passed to the next agent.

Agents participating in handoffs can be provided with a [`RECOMMENDED_PROMPT_PREFIX`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/handoff_prompt.py#L3), defined in [`src/agents/extensions/handoff_prompt.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/handoff_prompt.py), which instructs them on their role in a multi-agent system and how to execute transfers transparently to the user. This helps maintain consistent behavior and user experience in multi-agent workflows.

Various examples illustrate handoff mechanisms, including those that demonstrate message filtering and conditional handoffs, such as in [`examples/handoffs`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/handoffs). Additionally, multi-agent systems, such as the customer service example in [`examples/customer_service`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/customer_service) and the financial research agent in [`examples/financial_research_agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/financial_research_agent), showcase how handoffs enable collaboration between specialized agents to achieve complex tasks. These examples highlight how agent handoffs are integrated into practical applications. See [Multi-Agent Systems for Complex Tasks](https://codewiki.google/github.com/openai/openai-agents-python#ai-agent-examples-and-patterns-multi-agent-systems-for-complex-tasks) for further examples.

### Advanced Agent Design Patterns

link

zoom\_in

The framework supports various design patterns for orchestrating multiple agents to handle complex tasks, ranging from sequential execution to dynamic collaboration and iterative refinement.

For sequential task execution, deterministic flows ensure that agents process information in a predefined order with conditional branching. For example, a multi-stage process for generating a story might involve an agent creating an outline, followed by another agent checking its quality and genre, and then a final agent writing the story only if the outline meets specific criteria, as illustrated in [`examples/agent_patterns/deterministic.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/deterministic.py). This pattern uses structured outputs, such as a [`pydantic.BaseModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/openai_realtime.py#L725) for [`OutlineCheckerOutput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/deterministic.py#L23), to facilitate reliable decision-making between steps.

Dynamic routing and handoffs enable flexible task delegation among specialized agents. A triage agent can detect the language of a user request and route it to an appropriate language-specific agent (e.g., French, Spanish, or English), as demonstrated in [`examples/agent_patterns/routing.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/routing.py). This mechanism also supports streaming responses, providing a more interactive user experience.

The "agents as tools" pattern allows an orchestrating agent to dispatch messages to other agents that function as specialized tools. For instance, a central orchestrator can leverage dedicated translation agents (Spanish, French, Italian) to translate user messages. A synthesizer agent can then refine the combined output, as shown in [`examples/agent_patterns/agents_as_tools.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/agents_as_tools.py). Tools can also be conditionally enabled or disabled based on [`AppContext`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/agents_as_tools_conditional.py#L14) and [`is_enabled`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/tests/realtime/test_session.py#L225) predicates, allowing dynamic adaptation to user preferences or access levels, as explored in [`examples/agent_patterns/agents_as_tools_conditional.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/agents_as_tools_conditional.py).

Techniques for enforcing tool usage ensure that agents utilize specific functionalities when required. The [`ModelSettings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L59) class, with its [`tool_choice`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L81) parameter, can force an agent to call a particular tool. Different strategies for handling tool outputs are supported, such as sending the output back to the LLM for further processing, using the first tool result as the final output, or custom processing with a dedicated function, as detailed in [`examples/agent_patterns/forcing_tool_use.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/forcing_tool_use.py).

The "LLM-as-a-Judge" pattern facilitates iterative feedback and refinement. This involves one agent generating content (e.g., a story outline) and another agent evaluating it, providing feedback and a score. This process can loop, with the generator improving its output based on the evaluator's feedback, until a satisfactory result is achieved, as demonstrated in [`examples/agent_patterns/llm_as_a_judge.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/llm_as_a_judge.py).

Guardrails ensure robust agent behavior by validating inputs and outputs. An [`input_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L202) can prevent an agent from processing disallowed requests, such as math homework, by triggering an [`InputGuardrailTripwireTriggered`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/exceptions.py#L78) exception, as seen in [`examples/agent_patterns/input_guardrails.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/input_guardrails.py). Similarly, an [`output_guardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L284) can prevent an agent from generating responses containing sensitive data (e.g., phone numbers) by raising an [`OutputGuardrailTripwireTriggered`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/exceptions.py#L91) exception, as exemplified in [`examples/agent_patterns/output_guardrails.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/output_guardrails.py). Streaming guardrails extend this by continuously checking partial agent outputs during generation, allowing for early termination if violations occur, thereby enhancing efficiency and responsiveness, as shown in [`examples/agent_patterns/streaming_guardrails.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/streaming_guardrails.py).

Another pattern involves parallelizing agent execution to reduce latency or improve result quality. Multiple instances of an agent can run concurrently (e.g., translating a message into Spanish three times), and then another agent can select the best result from the generated options, as illustrated in [`examples/agent_patterns/parallelization.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/agent_patterns/parallelization.py).

### Model Context Protocol (MCP) Implementations

link

zoom\_in

The Model Context Protocol (MCP) enables AI agents to interact with external services and data sources through a standardized interface. This allows agents to dynamically access information, execute tools, and receive instructions, extending their capabilities beyond their core LLM.

MCP implementations demonstrate various server types and their applications.

- **Filesystem Interaction**: Agents can interact with local filesystems using an [`MCPServerStdio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L387). This allows agents to list directories and read file contents, as shown in [`examples/mcp/filesystem_example`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/filesystem_example). For example, an agent can be configured to read specific text files within a designated directory to answer questions or generate suggestions.

- **Git Repository Querying**: Similar to filesystem interaction, agents can query local Git repositories via [`MCPServerStdio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L387) communicating with a [`git MCP server`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L1). This enables agents to retrieve information about repository history, such as frequent contributors or recent changes, as illustrated in [`examples/mcp/git_example`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/git_example).

- **Dynamic Prompt Generation**: The framework supports dynamic generation of agent instructions through a local MCP prompt server, typically implemented using [`FastMCP`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/sse_example/server.py#L4). This allows for flexible configuration of agent behavior without hardcoding instructions. An example in [`examples/mcp/prompt_server`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/prompt_server) shows how a server can provide code review instructions based on parameters like focus and language, which an agent then uses for its task.

- **Server-Sent Events (SSE) for Tool Access**: Agents can utilize tools exposed by an SSE server via an [`MCPServerSse`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L489) instance. This setup demonstrates how an agent can trigger actions like arithmetic calculations, random word generation, or real-time weather information retrieval from an external service, as depicted in [`examples/mcp/sse_example`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/sse_example).

- **Streamable HTTP for General Tool Interaction**: [`MCPServerStreamableHttp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L596) enables agents to interact with general HTTP-based MCP servers. This is a versatile method for agents to perform actions like adding numbers, fetching weather data, or retrieving specific information via remote procedures, as shown in [`examples/mcp/streamablehttp_example`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/streamablehttp_example).

- **Customized HTTP Client Configurations**: For scenarios requiring specific network behaviors, the [`MCPServerStreamableHttp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L596) allows for customization of its underlying [`httpx.AsyncClient`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/util.py#L37) via a [`httpx_client_factory`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/mcp/server.py#L592). This enables fine-grained control over HTTP client settings such as SSL verification, timeouts, custom headers, and proxy configurations, as detailed in [`examples/mcp/streamablehttp_custom_client_example`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/streamablehttp_custom_client_example). This is useful for integrating with corporate networks, handling specific security requirements, or optimizing network performance.

- **Hosted MCP Tools**: Beyond local servers, the framework supports [`HostedMCPTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L302) for interacting with external hosted MCP services, often integrated with the OpenAI Responses API. These tools can incorporate approval workflows, allowing for human-in-the-loop validation of agent actions, or integrate with external services like Google Calendar. Examples in [`examples/hosted_mcp`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/hosted_mcp) demonstrate scenarios with and without approval mechanisms, and connections to external APIs.

The framework supports integration with various Large Language Model (LLM) providers beyond the default OpenAI models, enabling flexibility in model selection and deployment. This is achieved through mechanisms for configuring custom [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) clients, setting global default providers, and explicitly integrating with [`LiteLLM`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L32) for broader model support.

Custom model providers can be integrated by supplying a custom [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) client instance to an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133). This approach, demonstrated in [`examples/model_providers/custom_example_agent.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/custom_example_agent.py), allows developers to specify alternative API endpoints and keys for OpenAI-compatible models. For scenarios requiring a custom model provider to be used consistently across multiple agents, a global default [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) client can be configured using [`set_default_openai_client`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/_config.py#L15) and [`set_default_openai_api`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/_config.py#L22), as shown in [`examples/model_providers/custom_example_global.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/custom_example_global.py). This simplifies agent initialization by automatically applying the custom client configuration.

For more granular control or when different model backends are needed for distinct agent interactions, a custom [`ModelProvider`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L110) can be defined. This provider encapsulates the [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) client and can be passed explicitly to [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92) via [`RunConfig`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L179), allowing on-the-fly selection of the LLM backend. An example of this is found in [`examples/model_providers/custom_example_provider.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/custom_example_provider.py).

The framework also supports integrating a wide array of non-OpenAI models through [`LiteLLM`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L32). Developers can specify [`LiteLLM`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L32) models by prefixing the model name with [`litellm/`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L57), which automatically directs the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) to use the [`LitellmModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/models/litellm_model.py#L65). This integration is illustrated in [`examples/model_providers/litellm_auto.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/litellm_auto.py), showcasing the use of models like Anthropic's Claude. Alternatively, a [`LitellmModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/models/litellm_model.py#L65) instance can be directly configured and assigned to an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133), providing a more explicit way to connect to LiteLLM-supported providers, as detailed in [`examples/model_providers/litellm_provider.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/litellm_provider.py). This approach allows for dynamic specification of models and API keys, enhancing flexibility. Further details on model integration can be found in [Model Integration and Configuration](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration).

Regardless of the integration method, a common practice when working with custom model providers is to disable tracing using [`set_tracing_disabled`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tracing/__init__.py#L97). This is often necessary because custom providers may not fully support OpenAI's platform-specific tracing API, preventing potential errors or unexpected behavior. Examples such as [`examples/model_providers/custom_example_agent.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/custom_example_agent.py) and [`examples/model_providers/custom_example_global.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/custom_example_global.py) demonstrate this practice. Environment variables are consistently used across these examples ( [`EXAMPLE_BASE_URL`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/README.md?plain=1#L6), [`EXAMPLE_API_KEY`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/README.md?plain=1#L7), [`EXAMPLE_MODEL_NAME`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/main.py#L23)) to promote flexible deployment and avoid hardcoding sensitive information.

This section outlines the implementation and application of various specialized tools that extend the capabilities of AI agents within the framework. These tools enable agents to perform diverse tasks, from interacting with file systems and executing code to browsing the web and generating images, often incorporating safety and user oversight mechanisms.

One such capability is controlled file system manipulation. Agents can utilize an [`ApplyPatchTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L461) to propose and apply changes (create, update, delete) to a temporary workspace. A key aspect of this tool, demonstrated in [`examples/tools/apply_patch.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/apply_patch.py), is the integration of an [`ApprovalTracker`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/apply_patch.py#L12) and [`WorkspaceEditor`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/apply_patch.py#L32). These components ensure that any file system modifications require explicit user approval, preventing unintended operations. This mechanism fingerprints each proposed change and prompts the user for confirmation, enhancing security and control over the agent's actions.

For computational tasks, the [`CodeInterpreterTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L323) allows agents to generate and execute Python code. As illustrated in [`examples/tools/code_interpreter.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/code_interpreter.py), an agent equipped with this tool can tackle mathematical problems by writing and running code, with the process being observable through streamed events that reveal the generated code.

Automated web browser interaction is facilitated by the [`ComputerTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L241), which, when wrapping a [`LocalPlaywrightComputer`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/computer_use.py#L68), enables agents to navigate, search, and summarize web content. The example in [`examples/tools/computer_use.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/computer_use.py) shows an agent performing tasks like searching for news and summarizing articles, utilizing Playwright's capabilities for actions such as [`screenshot`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/computer.py#L23), [`click`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/computer.py#L27), [`type`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L456), and [`scroll`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/computer.py#L35).

Agents can also perform file searches against structured data using a [`FileSearchTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L195). Image generation capabilities are provided through the [`ImageGenerationTool`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L335). The demonstration in [`examples/tools/image_generator.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/image_generator.py) shows how an agent requests an image, and the system processes the generated output, decodes it, and displays it to the user.

### Real-time Voice and Interactive Agents

link

zoom\_in

The framework provides capabilities for constructing real-time, voice-driven AI agents, enabling interactive applications and integrations with telephony platforms. This involves continuous audio processing, conversation management, and the orchestration of voice-based workflows.

Web-based interactive applications can be built using a [`FastAPI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L390) backend for managing [`WebSocket`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L21) connections and a JavaScript/HTML frontend for user interaction, as exemplified in [`examples/realtime/app`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/app). This setup allows for real-time audio capture and playback, image uploads, and dynamic display of conversation history and agent activities. The backend handles [`WebSocket`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L21) communication, routes client events to a [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) for the AI agent, and streams agent responses back to the client. The frontend utilizes Web Audio API worklets for efficient audio recording and playback, including features like fading samples to prevent audio clicks during playback.

For command-line interfaces, the framework supports real-time, voice-driven interaction with advanced audio processing, including "barge-in" functionality. The [`NoUIDemo`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/cli/demo.py#L55) in [`examples/realtime/cli/demo.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/cli/demo.py) demonstrates continuous audio capture from a microphone, streaming to a [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27), and playing back real-time audio responses. A key feature is the ability for user speech to interrupt the agent's playback (barge-in), achieved by detecting user speech energy and signaling an [`interrupt_event`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/cli/demo.py#L69) to stop agent output. Audio playback includes a jitter buffer and graceful fade-out during interruptions for a smoother user experience. The [`RealtimePlaybackTracker`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/model.py#L29) informs the agent model about played audio segments, aiding in more informed decisions for interruptions and responses.

The framework also integrates with telephony platforms like Twilio for SIP and voice calls, as shown in [`examples/realtime/twilio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/twilio) and [`examples/realtime/twilio_sip`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/twilio_sip). The [`TwilioRealtimeTransportLayer`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/twilio/README.md?plain=1#L50) acts as an adapter, bridging communication between Twilio's Media Streams and the OpenAI Realtime API, handling protocol differences and audio format compatibility (G.711 μ-law at 8kHz for Twilio). Incoming phone calls trigger a server endpoint that responds with TwiML instructions to establish a [`WebSocket`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L21) connection, streaming audio between Twilio and the AI agent. The [`TwilioHandler`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/twilio/twilio_handler.py#L45) class manages the real-time conversation, buffering incoming audio, sending it to the [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27), and streaming synthesized audio back to Twilio. It also supports tool usage for information retrieval and incorporates a deterministic startup warm-up to accumulate initial audio before sending it to the agent, improving conversational flow. For SIP calls, the system accepts incoming calls via Twilio Elastic SIP Trunking, processes [`realtime.call.incoming`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/twilio_sip/server.py#L199) webhook events from OpenAI, and initiates interactions with a multi-agent system (e.g., a triage agent routing to specialized agents) while logging call transcripts and events.

Beyond the specific real-time implementations, the framework offers a general [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) for orchestrating end-to-end voice interactions, integrating Speech-to-Text (STT) and Text-to-Speech (TTS), managing workflows, and processing streamed audio input with activity detection for turn management. Examples in [`examples/voice`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/voice) demonstrate both static, command-line driven voice interactions with tool usage and agent handoff, and streamed, interactive applications with real-time transcription, agent conversation, and turn detection. This includes a [`SingleAgentVoiceWorkflow`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/workflow.py#L62) for agent logic and [`StreamedAudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L74) for continuous audio capture. For further details on the components used in real-time agents, refer to [Real-time Conversational Agents with RealtimeRunner](https://codewiki.google/github.com/openai/openai-agents-python#real-time-and-voice-enabled-agents-real-time-conversational-agents-with-realtimerunner) and [Voice Pipeline for End-to-End Voice Applications](https://codewiki.google/github.com/openai/openai-agents-python#real-time-and-voice-enabled-agents-voice-pipeline-for-end-to-end-voice-applications).

\# Configure ModelSettings to request detailed reasoning
agent = Agent(

The framework enables the extraction and utilization of an AI model's internal reasoning process alongside its final output, providing transparency into agent decision-making. This functionality is demonstrated through both streaming and non-streaming approaches.

To enable reasoning extraction, an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) is configured with [`ModelSettings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L59) that explicitly request [`Reasoning`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L30) with specified [`effort`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tools.md?plain=1#L229) and [`summary`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/.github/PULL_REQUEST_TEMPLATE/pull_request_template.md?plain=1#L1) levels. This tells the model to provide insight into its decision-making.

For non-streaming interactions, the [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92) method executes a query and returns a complete [`result`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/model_providers/litellm_auto.py#L25) object. Reasoning content can then be parsed from [`result.new_items`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/tools/file_search.py#L58), which contains [`ReasoningItem`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/items.py#L291) objects. The specific reasoning text is extracted from [`item.raw_item.summary[0].text`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/runner_example.py#L44). An example of this can be found in [`examples/reasoning_content/runner_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/runner_example.py).

For streaming interactions, [`Runner.run_streamed`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L69) initiates execution, and an asynchronous iterator yields events as the agent processes the request. Events are categorized by [`event.type`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/mcp.md?plain=1#L75) and [`event.data.type`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/workflow.py#L51). Specifically, [`"response.reasoning_summary_text.delta"`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/main.py#L53) events provide streaming reasoning content, while [`"response.output_text.delta"`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/streaming.md?plain=1#L9) events provide the streaming output text. This allows for real-time display and processing of both reasoning and final output. Examples of this are provided in [`examples/reasoning_content/gpt_oss_stream.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/gpt_oss_stream.py) and [`examples/reasoning_content/main.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/main.py). The [`examples/reasoning_content`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content) directory contains further demonstrations.

The ability to extract reasoning content is dependent on the capabilities of the underlying AI model. The examples often configure the [`MODEL_NAME`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/reasoning_content/main.py#L23) (e.g., defaulting to "gpt-5") via environment variables, indicating that this feature is model-specific.

| `RedisSession` | Scalable, persistent session memory | Redis-backed storage, TTL, custom key prefixes | `redis_session_example.py` |
| `DaprSession` | Cloud-native, distributed applications | Dapr state store for 30+ backends, TTL, consistency levels | `dapr_session_example.py` |

Agents maintain conversational context and history across multiple runs through session management, enabling continuous and coherent dialogues. The framework provides various session implementations to support diverse memory storage backends and advanced features.

The core mechanism for managing conversation history is defined by the [`SessionABC`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L53) protocol, which all session implementations adhere to. This protocol allows for the automatic storage and retrieval of conversational turns by the [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) before and after each agent execution. This abstraction simplifies agent development by removing the need for manual handling of conversation history. Methods such as [`get_items`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L20) retrieve conversation history, [`add_items`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L32) stores new turns, [`pop_item`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L40) removes the most recent turn, and [`clear_session`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L48) erases all history.

Several built-in session implementations are available:

- [`SQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/sqlite_session.py#L13), a default lightweight option, supports both in-memory and file-based persistence for storing conversation history. An example of its use is provided in [`examples/memory/sqlite_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/sqlite_session_example.py).
- [`SQLAlchemySession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/sqlalchemy_session.py#L52) offers a production-ready solution by integrating with any SQLAlchemy-supported database, such as PostgreSQL, MySQL, or SQLite. It supports initialization via a database URL or an existing SQLAlchemy engine, as demonstrated in [`examples/memory/sqlalchemy_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/sqlalchemy_session_example.py).
- [`OpenAIConversationsSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/openai_conversations_session.py#L22) integrates directly with OpenAI's Conversations API for history storage. Its usage is illustrated in [`examples/memory/openai_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/openai_session_example.py).
- [`RedisSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/redis_session.py#L41) provides a Redis-backed memory solution, suitable for scalable and persistent storage, including features like custom key prefixes for multi-tenancy and automatic Time-To-Live (TTL) for message expiration. An example is available in [`examples/memory/redis_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/redis_session_example.py).
- [`DaprSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/dapr_session.py#L56) integrates with Dapr's state management building block, enabling scalable and resilient session management in cloud-native and distributed environments. It supports features like TTL, consistency levels, and multi-tenancy with various backend stores. [`examples/memory/dapr_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/dapr_session_example.py) shows a practical application.

For advanced conversation management, [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) extends the basic SQLite functionality by offering features such as conversation branching, detailed usage analytics, and structured querying. Branching allows developers to create and switch between alternative conversation paths from any user message, facilitating scenario testing without altering the main conversation flow. This session also tracks token usage and request counts per turn and session. This is detailed in [`docs/sessions/advanced_sqlite_session.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/sessions/advanced_sqlite_session.md) and demonstrated in [`examples/memory/advanced_sqlite_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/advanced_sqlite_session_example.py).

To address security concerns, [`EncryptedSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/encrypt_session.py#L98) wraps any underlying session implementation to provide transparent encryption and automatic Time-To-Live (TTL) functionality for conversation data. It uses HKDF (HMAC-based Key Derivation Function) to derive unique Fernet keys per session, ensuring data is encrypted before storage and decrypted upon retrieval. Messages older than the configured TTL are silently ignored. The implementation of [`EncryptedSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/encrypt_session.py#L98) is described in [`docs/sessions/encrypted_session.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/sessions/encrypted_session.md) and showcased in [`examples/memory/encrypted_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/encrypted_session_example.py).

The framework's [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92) and [`Runner.run_sync`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L56) methods accept a [`session`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L11) argument, enabling automatic memory management and ensuring agents leverage stored history for context. This protocol-oriented design allows developers to implement custom memory backends by adhering to the [`SessionABC`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/session.py#L53) interface.

### Conversation Branching and Advanced Management

The framework provides [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) for intricate conversation control within multi-agent workflows. This session implementation extends the basic SQLite-based storage with capabilities for managing complex conversational states, detailed usage tracking, and structured querying of conversation history.

A key feature of [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) is its support for conversation branching, as demonstrated in [`examples/memory/advanced_sqlite_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/advanced_sqlite_session_example.py). This allows developers to explore alternative conversation paths from any user message, facilitating scenario testing or "what-if" analyses without affecting the main dialogue flow. Methods like [`create_branch_from_turn`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L542) and [`create_branch_from_content`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L608) enable the creation of new, independent branches. These branches can then be managed using [`list_branches`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L744), [`switch_to_branch`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L631) to change the active conversation timeline, and [`delete_branch`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L664). This isolation ensures that modifications or new messages in one branch do not impact other branches, preserving conversational integrity.

The [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) also incorporates detailed usage tracking, storing token usage (input, output, total) and request counts per turn and session. This functionality, crucial for cost analysis and performance monitoring, relies on explicit calls to [`store_run_usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L236) after each agent run to persist usage data. Aggregated and turn-specific usage statistics can be retrieved using [`get_session_usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L1061) and [`get_turn_usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L1121). The session further stores granular JSON breakdowns of token usage ( [`input_tokens_details`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/usage.py#L35), [`output_tokens_details`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/usage.py#L42)).

For enhanced analysis and debugging, the [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) provides structured querying capabilities. This includes [`get_conversation_by_turns`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L989) to organize messages by user turn number, [`get_tool_usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L1027) to retrieve statistics on tool invocations, and [`find_turns_by_content`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L933) to locate specific content within the conversation history. The session automatically stores metadata for each message, such as message type, tool name, sequence number, user turn number, branch turn number, and timestamps, which are then used by these querying mechanisms. While [`EncryptedSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/encrypt_session.py#L98) can be used to secure conversation data, it's important to note that content-based searches may not function effectively due to the encrypted data, as described in [Encrypted Sessions with Time To Live (TTL)](https://codewiki.google/github.com/openai/openai-agents-python#agent-memory-and-session-management-encrypted-sessions-with-time-to-live-ttl).

The [`AdvancedSQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/advanced_sqlite_session.py#L18) uses an SQLite database as its backend, enhancing the schema of the basic [`SQLiteSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/memory/sqlite_session.py#L13) with additional tables for message structure and turn usage. This design allows for persistent storage and complex data retrieval, supporting the advanced features for conversation analysis and branching detailed in [`docs/sessions/advanced_sqlite_session.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/sessions/advanced_sqlite_session.md). For other session management options, including distributed environments, refer to [Distributed Session Management with Dapr and Redis](https://codewiki.google/github.com/openai/openai-agents-python#agent-memory-and-session-management-distributed-session-management-with-dapr-and-redis).

### Distributed Session Management with Dapr and Redis

link

zoom\_in

The framework provides mechanisms for agents to manage conversation history in distributed environments, leveraging both Redis and Dapr for scalable and resilient session management. These solutions address the need for agents to maintain context across multiple interactions in cloud-native deployments.

The [`RedisSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/redis_session.py#L41) ( [`examples/memory/redis_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/redis_session_example.py)) enables agents to store and retrieve conversation history using a Redis instance. This approach offers persistence and scalability, crucial for applications where an agent's memory needs to survive application restarts or be accessible by multiple agent instances. [`RedisSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/redis_session.py#L41) supports advanced features like custom key prefixes, which allow for multi-tenancy by isolating sessions belonging to different users or logical groups within the same Redis instance. It also incorporates Time-To-Live (TTL) functionality, automatically expiring old messages to manage data retention and reduce storage overhead.

For more complex cloud-native architectures, [`DaprSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/dapr_session.py#L56) ( [`examples/memory/dapr_session_example.py`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/memory/dapr_session_example.py)) integrates with Dapr's state management building block. Dapr, a Distributed Application Runtime, abstracts the underlying state store, allowing developers to use various backends (such as Redis, PostgreSQL, or others) without changing agent code. This flexibility supports horizontal scaling and multi-region deployments. [`DaprSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/dapr_session.py#L56) provides configurable consistency levels (e.g., eventual or strong consistency) to align with application requirements for data integrity in distributed settings. Similar to [`RedisSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/memory/redis_session.py#L41), it also includes support for TTL, enabling message expiration, and facilitates multi-tenancy through session ID prefixes. The setup for Dapr components, including environment configuration and Docker container management, is supported to simplify development and deployment. For further details on agent memory and session management, refer to the [Agent Memory and Session Management](https://codewiki.google/github.com/openai/openai-agents-python#agent-memory-and-session-management) section.

The [`get_default_model_settings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/default_models.py#L49) function in [`docs/models/index.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md) can retrieve these default settings.

Integration with non-OpenAI models is largely facilitated by LiteLLM. This requires the installation of the [`litellm`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L320) dependency group. Models are then specified with a [`litellm/`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L57) prefix (e.g., [`litellm/anthropic/claude-3-5-sonnet-20240620`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L60)). The [`LitellmModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/extensions/models/litellm_model.py#L65) class, described in [`docs/models/litellm.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/litellm.md), is used to instantiate an [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) with LiteLLM-supported models. This integration also allows for tracking usage data (tokens, requests) by setting [`ModelSettings(include_usage=True)`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L34), making usage available via [`result.context_wrapper.usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L18).

Custom Large Language Model (LLM) providers and clients can be configured through several methods. A global [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) instance can be set for OpenAI-compatible endpoints using [`set_default_openai_client`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/_config.py#L15). Alternatively, a [`ModelProvider`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L110) can be specified at the [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92) level, or different [`Model`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L36) implementations can be directly assigned to individual [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) instances. This flexibility allows for mixing and matching various model providers within a single workflow.

When working with diverse models, developers should be aware of potential feature differences. Many non-OpenAI providers may not support the Responses API, necessitating the use of [`OpenAIChatCompletionsModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/openai_chatcompletions.py#L38). Other variations in features like multimodal input or hosted tools also require careful consideration to prevent client errors. For more details on these considerations, refer to [Handling Model-Specific Features and Limitations](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration-handling-model-specific-features-and-limitations).

The framework provides several advanced methods for integrating and configuring custom Large Language Model (LLM) providers and clients, offering flexibility beyond the default OpenAI models.

To establish a global configuration for OpenAI-compatible endpoints, a custom [`AsyncOpenAI`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/config.md?plain=1#L13) instance can be set. This allows all agents within the application to utilize a consistent client for interacting with various OpenAI-API-compatible services.

For scenarios requiring different model providers within a single workflow, the [`ModelProvider`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L110) class enables specifying a custom provider at the [`Runner.run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L92) level. This means that during the execution of a [`Runner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L294) instance, a particular [`ModelProvider`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L110) can be designated to handle model interactions for all agents involved, effectively overriding individual agent configurations.

Alternatively, for more granular control, different [`Model`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/interface.py#L36) implementations can be directly assigned to individual [`Agent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent.py#L133) instances. This approach facilitates mixed provider scenarios where some agents might use OpenAI models, others might integrate through LiteLLM, and still others might employ a custom model implementation, all within the same multi-agent system. This direct assignment allows for fine-tuned selection of model capabilities and costs per agent.

Integrating non-OpenAI models primarily relies on LiteLLM. Once the [`litellm`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L320) dependency group is installed, models can be specified using a [`litellm/`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L57) prefix. The framework supports tracking usage data (tokens, requests) from LiteLLM responses by enabling [`include_usage=True`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L34) in [`ModelSettings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/model_settings.py#L59), which makes this information accessible via [`result.context_wrapper.usage`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/usage.md?plain=1#L18). This ensures consistent usage metrics across various model types. More details on this integration can be found in [Integrating Non-OpenAI Models via LiteLLM](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration-integrating-non-openai-models-via-litellm).

Developers should be aware of potential limitations when working with diverse models. For instance, many non-OpenAI providers may not support the Responses API, requiring the use of [`OpenAIChatCompletionsModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/models/openai_chatcompletions.py#L38) for chat completions. Similarly, structured output capabilities, particularly those relying on [`json_schema`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/agent_output.py#L32), might vary, potentially leading to [`BadRequestError`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/models/index.md?plain=1#L176) if the selected model does not support these features. Multimodal input and hosted tool support also differ across providers, necessitating careful consideration during model selection and agent configuration to avoid errors. These considerations are further outlined in [Handling Model-Specific Features and Limitations](https://codewiki.google/github.com/openai/openai-agents-python#model-integration-and-configuration-handling-model-specific-features-and-limitations).

## Real-time and Voice-Enabled Agents

link

zoom\_in

This section describes the framework's capabilities for building AI agents that interact in real-time, often through voice. It covers the core components and design patterns for creating conversational flows, managing low-latency audio and text processing, handling interruptions, and orchestrating voice applications from agentic workflows. This includes speech-to-text (STT) and text-to-speech (TTS) functionalities, as well as streaming audio input and output.

The framework supports real-time, voice-enabled agents through components like [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27), [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18), and [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63). The [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27) is configured with instructions and tools, similar to a standard agent, but with specific considerations for real-time interactions, such as model choice at the session level and voice configuration. The [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18) orchestrates the real-time interaction, while the [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) manages the active conversation, including sending audio or text input and processing event streams. This event-driven architecture, typically implemented with [`asyncio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L72), allows for immediate reactions to events like audio input, transcripts, tool calls, and handoffs, which is crucial for natural, low-latency voice conversations.

A key feature for voice-enabled interactions is the robust handling of interruptions. The system automatically stops current audio generation when a user speaks, facilitating a more natural conversational flow. Guardrails, particularly [`OutputGuardrail`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/guardrail.py#L134), can be applied to [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27) s to ensure safety and compliance by checking agent outputs. These guardrails are debounced and run periodically, balancing performance with safety in high-speed real-time environments.

For orchestrating end-to-end voice applications, the [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) is a central component. It integrates STT for transcribing incoming audio, executes a defined agentic workflow based on the transcription, and then uses TTS to convert the workflow's textual output back into audio. This pipeline is highly configurable, allowing for specification of workflows (e.g., [`SingleAgentVoiceWorkflow`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/workflow.py#L62)), STT and TTS models, and fine-tuning through [`VoicePipelineConfig`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline_config.py#L12). The [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) can process both pre-recorded audio via [`AudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L41) and real-time audio streams using [`StreamedAudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L74). For real-time streams, "Activity Detection" is used to identify when a user has finished speaking, thereby triggering the workflow at the appropriate moment. The [`run()`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L133) method of [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) returns a [`StreamedAudioResult`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/result.py#L28) that can be iterated over asynchronously to handle various [`VoiceStreamEvent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L44) objects, such as [`VoiceStreamEventAudio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L12) for audio chunks and [`VoiceStreamEventLifecycle`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L23) for turn management.

Tracing capabilities are built into voice pipelines, allowing for monitoring and debugging of complex voice interactions. The [`VoicePipelineConfig`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline_config.py#L12) enables detailed tracing configuration, including options to control the inclusion of sensitive data and raw audio in traces.

The framework also provides practical examples and mechanisms for integrating these real-time and voice agents with various communication channels. This includes SIP integration for telephony applications through components like [`OpenAIRealtimeSIPModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/openai_realtime.py#L955), which reuses the existing agent flow for voice calls. Web-based interactive applications can also leverage these agents, showcasing their versatility across different deployment scenarios.

### Real-time Conversational Agents with RealtimeRunner

link

zoom\_in

Real-time conversational agents are enabled through the interaction of [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27), [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18), and [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) components. A [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27) defines the agent's behavior and persona, configured with instructions, tools, and handoffs. While similar to a standard agent, specific configurations are applied for real-time applications, such as model choice at the session level and voice configuration per agent. The [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18) manages the overall configuration and initiates a [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) via its [`run`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L296) method, which orchestrates the real-time interaction.

A [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) represents a single conversational exchange, handling the sending of audio or text inputs and listening for a variety of real-time events. These events can include agent lifecycle updates ( [`agent_start`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L70), [`agent_end`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L72)), tool calls ( [`tool_start`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L123), [`tool_end`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L123)), [`handoff`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/handoffs/__init__.py#L86) events between agents, audio streams ( [`audio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/items.py#L27), [`audio_end`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L121)), and [`audio_interrupted`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L122) events. The framework leverages an event-driven architecture and [`asyncio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L72) for asynchronous operations, which is crucial for processing continuous event streams.

Key to natural conversational flows is robust interruption handling, where the system automatically stops current audio generation when a user speaks. Output guardrails can also be applied to [`RealtimeAgent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/agent.py#L27) s or a [`run_config`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tools.md?plain=1#L289) to check for sensitive or undesirable content. These guardrails are debounced to balance performance with safety, triggering [`guardrail_tripped`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/guide.md?plain=1#L151) events without raising exceptions.

The [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18)'s configuration ( [`config`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/mkdocs.yml#L79)) plays a central role in setting up [`model_settings`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/run.py#L190) (e.g., [`model_name`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/model.py#L69), [`voice`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/model.py#L25), [`modalities`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/llms.txt#L5), audio formats), [`input_audio_transcription`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L52) (e.g., using Whisper), and [`turn_detection`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/model.py#L116) parameters. These parameters, such as [`type`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/tool.py#L456), [`threshold`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L204), [`silence_duration_ms`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L205), and [`prefix_padding_ms`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime/quickstart.md?plain=1#L206), control when the agent responds based on voice activity detection (VAD). For examples of these components in action, see [Real-time Voice and Interactive Agents](https://codewiki.google/github.com/openai/openai-agents-python#ai-agent-examples-and-patterns-real-time-voice-and-interactive-agents). The underlying [`RealtimeModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/model.py#L150) provides the interface to the real-time model, typically OpenAI's WebSocket implementation, allowing for advanced operations through listeners. Further details on real-time agent capabilities and implementation can be found in the documentation within [`docs/realtime`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/realtime).

### Voice Pipeline for End-to-End Voice Applications

link

zoom\_in

The [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) orchestrates end-to-end voice interactions, integrating Speech-to-Text (STT) and Text-to-Speech (TTS) capabilities with agentic workflows. This component processes audio input, executes an agent's logic based on the transcribed text, and converts the agent's response back into audio for output. It is configurable through [`VoicePipelineConfig`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline_config.py#L12) (defined in [`docs/voice/pipeline.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/voice/pipeline.md)), which allows for specification of the [`workflow`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/mcp/prompt_server/README.md?plain=1#L17) instance, [`speech-to-text`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tracing.md?plain=1#L38) and [`text-to-speech`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/tracing.md?plain=1#L39) models, and tracing options (detailed further in [Tracing and Debugging Agent Workflows](https://codewiki.google/github.com/openai/openai-agents-python#multi-agent-llm-workflow-framework-tracing-and-debugging-agent-workflows)).

The pipeline's execution is initiated via its [`run()`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L133) method, which can accept either [`AudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L41) for pre-recorded audio or [`StreamedAudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L74) for real-time streams. For [`StreamedAudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L74), the system employs activity detection to identify when a user has finished speaking, ensuring the agent workflow is triggered at appropriate conversational turns. The [`run()`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/README.md?plain=1#L133) method returns a [`StreamedAudioResult`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/result.py#L28) object, which provides an asynchronous iterator for handling events as they occur. These events, derived from [`VoiceStreamEvent`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L44) (found in [`docs/voice/pipeline.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/voice/pipeline.md)), include audio chunks ( [`VoiceStreamEventAudio`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L12)), lifecycle updates (e.g., [`turn_started`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/voice/pipeline.md?plain=1#L75), [`turn_ended`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/voice/pipeline.md?plain=1#L75) from [`VoiceStreamEventLifecycle`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L23)), and error notifications ( [`VoiceStreamEventError`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/events.py#L34)). This event-driven approach enables real-time processing and dynamic reaction throughout the voice interaction.

An example of setting up a voice-enabled agent, including agent definition with handoffs and tool usage, and the execution of a [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) with [`AudioInput`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/input.py#L41), is demonstrated in [`docs/voice/quickstart.md`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/docs/voice/quickstart.md). For integration into various communication channels, this framework supports connecting voice-enabled agents with telephony systems via SIP (Session Initiation Protocol) and web-based interactive applications. ### Integrating Voice-Enabled Agents with Telephony and Web

link

zoom\_in

The framework facilitates the deployment of real-time and voice-enabled agents across diverse communication platforms, including telephony and web-based interactive applications.

For telephony integration, the [`OpenAIRealtimeSIPModel`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/openai_realtime.py#L955) allows direct interaction with the Realtime Calls API, enabling agents to engage in SIP-based voice calls. This component leverages the existing agent workflow definitions to extend conversational AI capabilities to traditional phone systems.

In web environments, the system supports the creation of interactive applications where agents can process real-time audio and text inputs and generate corresponding audio responses. This is managed through components like [`RealtimeRunner`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/runner.py#L18) and [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63), which handle persistent connections to real-time APIs and manage event streams for natural, low-latency voice interactions. Developers can integrate these agents into web applications to provide conversational interfaces, as demonstrated in examples located in [`examples/realtime/app`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/examples/realtime/app). The event-driven nature of the [`RealtimeSession`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/realtime/session.py#L63) allows for dynamic handling of audio, transcripts, tool calls, and handoffs, enabling adaptive conversational flows.

The [`VoicePipeline`](https://github.com/openai/openai-agents-python/blob/0dae2f0f1f2c5ac1a49fd54db56c60d69b93674c/src/agents/voice/pipeline.py#L15) further extends these capabilities by orchestrating end-to-end voice interactions, integrating speech-to-text (STT) and text-to-speech (TTS) functionalities with an agentic workflow. This pipeline, detailed in [Voice Pipeline for End-to-End Voice Applications](https://codewiki.google/github.com/openai/openai-agents-python#real-time-and-voice-enabled-agents-voice-pipeline-for-end-to-end-voice-applications), processes streamed audio inputs with activity detection to manage turn-taking and ensure coherent conversations in interactive settings.
