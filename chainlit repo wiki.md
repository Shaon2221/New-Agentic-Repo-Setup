This software repository provides a framework for building, deploying, and managing conversational AI applications. It offers a structured environment for creating AI-driven chat experiences, encompassing the necessary infrastructure for user interaction and system operation.

The system's functional areas include:

- The backend, built with [`FastAPI`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L44), provides an event-driven architecture. It processes conversational flow and manages components such as actions, messages, and steps. These elements represent interactive UI elements, communication units, and internal AI operations respectively. See [Core Backend Architecture and Event Handling](https://codewiki.google/github.com/chainlit/chainlit#core-conversational-ai-application-core-backend-architecture-and-event-handling).
- A React-based frontend manages the user interface, including chat session displays, interactive elements, and state management. It dynamically renders rich message content such as multimedia, data visualizations, and custom interactive components. [Frontend Application Development](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development) details the UI structure and interactions.
- Reusable UI components and a React client library facilitate integration into various web environments. This includes an embeddable [`Chainlit Copilot`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) widget and a React client library with hooks for seamless backend communication. [Reusable UI Components and React Integration](https://codewiki.google/github.com/chainlit/chainlit#reusable-ui-components-and-react-integration) provides further insights.
- A command-line interface (CLI) handles the application's lifecycle. It manages startup, configuration, environment setup, and validation of user applications. [Application Lifecycle and Configuration](https://codewiki.google/github.com/chainlit/chainlit#application-lifecycle-and-configuration) explains these tools.
- User authentication uses JSON Web Tokens and cookie-based session management. It also supports integration with OAuth providers. This secures user access and manages sessions. Refer to [User Authentication and Authorization](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization).
- A unified data layer supports various database and object storage backends. It stores user data, chat threads, steps, and elements. This modular design accommodates different storage solutions. Details are in [Data Persistence and Storage](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage).
- WebSocket connections enable real-time communication between the backend and frontend for dynamic updates. [`FastAPI`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L44) endpoints expose core functionalities for authentication, thread management, and file operations. [Real-time Communication and API Endpoints](https://codewiki.google/github.com/chainlit/chainlit#real-time-communication-and-api-endpoints) elaborates on this.
- The system integrates with AI frameworks like LangChain, LlamaIndex, and OpenAI to provide observability for Large Language Model (LLM) operations. This includes visualization and debugging of AI model processes within the UI. See [AI Framework Integrations and Observability](https://codewiki.google/github.com/chainlit/chainlit#ai-framework-integrations-and-observability).
- Integration with external services, such as Discord, enables AI assistants to operate on different platforms. This functionality handles messages, user interactions, and feedback within those platforms. [External Service Integrations](https://codewiki.google/github.com/chainlit/chainlit#external-service-integrations) covers these capabilities.

## Core Conversational AI Application

link

zoom\_in

The core of the Chainlit project provides the foundational elements for building and managing conversational AI applications. This includes the infrastructure for creating, deploying, and operating AI-driven chat experiences by defining the overall structure, core components, and their interactions.

The project's development workflow and community contributions are managed through the [`.github`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.github) directory, which standardizes issue reporting and provides development guidelines. This ensures consistency in contributions and aids maintainers in overseeing the project. Release processes are documented in [`RELENG.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/RELENG.md), detailing semantic versioning, changelog updates, and GitHub release procedures, while [`CHANGELOG.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md) provides a historical record of all modifications. Contribution guidelines are outlined in [`CONTRIBUTING.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CONTRIBUTING.md), covering local development setup, application and UI execution from source, and testing procedures.

The backend, located in [`backend`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend), is responsible for the application's lifecycle, configuration, real-time communication, authentication, and data persistence. Its build process, managed by [`backend/build.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py), integrates with [`hatchling`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py#L8) to automate dependency installation and UI asset bundling, ensuring that all necessary static assets are available for deployment. The core backend logic within [`backend/chainlit`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit) establishes an event-driven architecture that facilitates interactions between AI components and the user interface.

For comprehensive quality assurance, end-to-end testing is conducted using Cypress, with tests located in [`cypress`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress). These tests validate user interactions, UI rendering, and backend integrations across various features, using Python scripts to simulate application logic. The Cypress configuration in [`cypress.config.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress.config.ts) manages the lifecycle of the Chainlit application during testing, ensuring isolated and controlled environments for each test run.

The frontend application, residing in [`frontend`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend), handles user authentication, chat session management, interactive UI components, internationalization, and API interactions. It provides the user-facing interface for Chainlit applications.

The project also includes reusable UI components and a React client library in [`libs`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs). These libraries, such as the Chainlit Copilot widget and the [`@chainlit/react-client`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L69) library, offer tools for embedding interactive chat experiences into various web applications and integrating with the Chainlit backend through React hooks and an API client. Further details on this can be found in [Reusable UI Components and React Integration](https://codewiki.google/github.com/chainlit/chainlit#reusable-ui-components-and-react-integration).

The application's lifecycle and configuration are primarily managed through command-line interface (CLI) tools, which handle application startup, environment setup, and user application validation. More information on this is available in [Application Lifecycle and Configuration](https://codewiki.google/github.com/chainlit/chainlit#application-lifecycle-and-configuration).

User authentication and authorization are implemented using JWTs and cookie-based session management, along with integration capabilities for OAuth providers. This ensures secure access and user management within Chainlit applications. See [User Authentication and Authorization](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization) for more details.

Data persistence is managed through a unified data layer interface, which supports various database and object storage backends, allowing for flexible storage of user data, chat threads, and other elements. [Data Persistence and Storage](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage) provides additional information on this.

Real-time communication with the frontend is achieved using WebSockets, and the backend exposes its functionalities through FastAPI endpoints, facilitating dynamic updates and interactions. [Real-time Communication and API Endpoints](https://codewiki.google/github.com/chainlit/chainlit#real-time-communication-and-api-endpoints) elaborates on this infrastructure.

Finally, Chainlit integrates with popular AI frameworks like LangChain, LlamaIndex, and OpenAI to provide enhanced observability and facilitate visualization and debugging of AI model operations within the Chainlit UI. This is discussed further in [AI Framework Integrations and Observability](https://codewiki.google/github.com/chainlit/chainlit#ai-framework-integrations-and-observability). External service integrations, such as with Discord, are also supported, enabling AI assistants to operate across different platforms. This is covered in [External Service Integrations](https://codewiki.google/github.com/chainlit/chainlit#external-service-integrations).

### Core Backend Architecture and Event Handling

link

zoom\_in

The core of the Chainlit application's backend is defined within the [`backend/chainlit`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit) directory, which establishes an event-driven architecture designed to manage conversational AI experiences. This architecture is built upon a FastAPI application that serves API endpoints and facilitates real-time communication with the frontend via WebSockets.

The backend provides a structured approach to defining and managing the conversational flow through several core components:

- **Actions ( [`Action`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/action.py#L12)):** These represent interactive UI elements, such as buttons, that users can engage with in the chat interface. An [`Action`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/action.py#L12) object includes a name, payload, label, and an optional icon, and is designed to trigger specific callbacks in the backend when interacted with. The asynchronous [`send`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L359) and [`remove`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L340) methods manage their lifecycle within the UI.
- **Messages ( [`Message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/message.py#L199)):** The fundamental unit of communication in Chainlit, [`Message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/message.py#L199) objects encapsulate content, author information, and metadata. Various specialized message types, such as [`AskUserMessage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/message.py#L343) for prompting user input or [`ErrorMessage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/message.py#L304) for conveying issues, facilitate diverse conversational interactions. Messages can be sent, updated, or removed asynchronously from the UI.
- **Steps ( [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164)):** Steps provide a mechanism for observability and visualization of processes occurring in the backend. These can represent stages in an AI agent's thought process, tool invocations, or other internal operations. They allow developers to track and display the progression of complex tasks within the chat interface, and are often used to instrument integrations with AI frameworks.
- **Tasks ( [`Task`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L317), [`TaskList`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L334)):** Tasks allow the application to present a list of steps or operations to the user, often indicating progress or completion. [`TaskList`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L334) groups multiple [`Task`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L317) objects, providing a structured way to display a sequence of activities.
- **Users ( [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29)):** The [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object represents the individual interacting with the Chainlit application. User information is essential for authentication, authorization, and personalizing the conversational experience.

The backend leverages an extensive system of **event callbacks** for customization and integration. Developers can register functions using decorators like [`@on_chat_start`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/hello.py#L6), [`@on_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/tests/test_callbacks.py#L111), and [`@action_callback`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/tests/test_callbacks.py#L161) to execute custom logic at various points in the application's lifecycle or in response to user actions. For example, [`@on_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/tests/test_callbacks.py#L111) allows developers to define how the application responds when a user sends a message.

The foundation for these functionalities is a **FastAPI application**, defined in [`backend/chainlit/server.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py). This server handles requests for project settings, manages file uploads and retrieval, and serves static assets. It uses [`CORSMiddleware`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L32) to manage Cross-Origin Resource Sharing and [`lifespan`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L87) events for application startup and shutdown procedures.

**Real-time communication** between the backend and the frontend is a critical aspect, powered by [`socketio.AsyncServer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L225). The [`ChainlitEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L154), located in [`backend/chainlit/emitter.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py), manages this communication channel, sending events like [`send_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L77), [`send_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L61), and [`send_token`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L133) to update the UI dynamically. This real-time interaction ensures that the conversational interface remains responsive and synchronized with backend operations. The [`ChainlitContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/context.py#L23), managed via Python's [`ContextVar`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/context.py#L3) as described in [`backend/chainlit/context.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/context.py), provides access to session information, the emitter, and the current step, ensuring that contextual data is available throughout asynchronous execution flows.

Authentication is handled via JWT-based and cookie-based session management. See [JWT-based Authentication and Secret Management](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization-jwt-based-authentication-and-secret-management) and [Cookie-based Session Management](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization-cookie-based-session-management) for more details. Data persistence is managed through a unified data layer interface, allowing for flexible storage backends. See [Unified Data Layer Interface and Implementations](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage-unified-data-layer-interface-and-implementations) and [Object Storage Clients for Elements](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage-object-storage-clients-for-elements) for more information.

### Development Workflow and Community Contributions

For Node.js dependencies, [`pnpm`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55) is utilized for installation via [`pnpm install`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/package.json#L21), building the UI with [`pnpm run buildUi`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/package.json#L21), and running frontend tests with [`pnpm test`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55).

The development server setup involves running the backend application using [`chainlit run`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) and the frontend development server with [`pnpm run dev`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55). This allows developers to work on both components concurrently. Code quality is maintained through linting and formatting; [`pnpm run lint`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55) addresses both UI and Python linting, while [`pnpm run formatUi`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/package.json#L21) and [`uv run ruff format`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L5) handle formatting for the UI and Python code, respectively. Before committing, developers are encouraged to run [`pnpm run lint`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55) to ensure compliance with CI requirements, as these checks are part of the automated workflow.

Community contributions are streamlined through predefined issue templates located in the [`.github/ISSUE_TEMPLATE`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.github/ISSUE_TEMPLATE) directory. These templates ensure that bug reports, such as those generated from [`.github/ISSUE_TEMPLATE/bug_report.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.github/ISSUE_TEMPLATE/bug_report.md), and feature requests, like those submitted via [`.github/ISSUE_TEMPLATE/feature_request.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.github/ISSUE_TEMPLATE/feature_request.md), provide all necessary information for triage and resolution. The overall development guidelines, including information on dependency management, building, testing, and validation, are detailed in [`.github/copilot-instructions.md`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.github/copilot-instructions.md).

### End-to-End Testing Framework

link

zoom\_in

Chainlit applications utilize an end-to-end testing framework to validate functionality, user interactions, and backend integration. This framework employs Cypress for UI validation and Python scripts to simulate backend application logic. The tests cover a wide range of features, including user interaction with actions and interactive prompts, handling of various file types, authentication mechanisms, and application configuration.

The testing suite verifies features such as action execution, message editing, and the dynamic removal of UI elements. For instance, tests in [`cypress/e2e/action`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/action) validate that user actions trigger their respective callbacks and that actions can be dynamically removed from messages. The display and functionality of various elements like audio, custom components, dataframes, images, PDFs, and text are confirmed through tests such as those found in [`cypress/e2e/audio_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/audio_element), [`cypress/e2e/custom_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/custom_element), and [`cypress/e2e/elements`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/elements). File uploads, including specific file types and rejection of unsupported ones, are verified by tests in [`cypress/e2e/ask_file`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/ask_file) and [`cypress/e2e/ask_multiple_files`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/ask_multiple_files).

Authentication flows, including custom and password-based authentication, and user environment variable management, are also validated. The [`cypress/e2e/auth`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth) directory, for example, tests custom authentication mechanisms and the integration of the Copilot widget with these flows. Application configuration, such as dynamic chat settings, custom commands, and theme application, is also thoroughly tested to ensure proper functionality and persistence. This includes validating that exceptions raised during chat initiation are correctly displayed in the UI, as demonstrated by tests in [`cypress/e2e/error_handling`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/error_handling).

The framework also integrates specific AI framework callback functionalities, such as those for LlamaIndex, to ensure their UI visualization. This comprehensive approach to end-to-end testing ensures the reliability and consistency of Chainlit applications across different user interactions and configurations.

### Build Process and Asset Management

link

zoom\_in

The application integrates frontend assets directly into the backend Python package during its build process. This involves automating the installation of JavaScript dependencies, building the user interface (UI) components, and then incorporating these compiled assets into the Python distribution.

The build process is initiated via a [`hatchling`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py#L8) build hook, which invokes the [`build`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py#L70) function in [`backend/build.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py). This function first identifies the project root and checks for a [`package.json`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/RELENG.md?plain=1#L20) file. If present, it uses [`pnpm`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L55) to install the necessary frontend and "copilot" dependencies and then builds their respective UI assets. After the assets are built, the system copies the compiled frontend and copilot distribution directories into the Python backend's [`dist`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.eslintignore#L2) folders. This ensures that when the Python package is installed, all required static assets are bundled with it, allowing the backend to serve them directly.

The [`build`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/build.py#L70) function handles errors during subprocess execution and file operations, providing informative messages and ensuring a graceful failure if any step of the build process encounters an issue. This integration streamlines deployment by packaging the frontend and backend components into a single, self-contained Python distribution.

## Frontend Application Development

zoom\_in

The frontend of the Chainlit application, located in the [`frontend`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend) directory, is a React- and TypeScript-based single-page application built with Vite and Tailwind CSS. It provides the user interface for interacting with conversational AI applications, managing chat sessions, and visualizing AI model operations.

The application's entry point is [`frontend/index.html`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/index.html), which establishes the basic HTML structure, loads essential assets such as fonts and CSS for mathematical typesetting, and serves as the mount point for the React application. The core logic is initiated by [`frontend/src/main.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/main.tsx), which sets up internationalization, global API client context, and Recoil-based state management.

The [`AppWrapper`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/AppWrapper.tsx#L13) component, defined in [`frontend/src/AppWrapper.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/AppWrapper.tsx), handles initial application setup. This includes managing user authentication, dynamically loading language translations, and establishing inter-window communication for embedded contexts. Upon successful initialization, it renders the main [`App`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/App.tsx#L27) component, located in [`frontend/src/App.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/App.tsx). This component orchestrates the application's global state, including user authentication status, overall configuration, and chat session connections. It also applies the UI theme and handles global notifications.

Client-side routing, configured in [`frontend/src/router.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/router.tsx) using [`react-router-dom`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/App.tsx#L3), defines the navigation paths for various pages, such as the home interface, environment variable settings, individual chat threads, login, and authentication callbacks. This setup ensures that navigation is handled dynamically without requiring full page reloads.

The [`frontend/src/pages`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/pages) directory contains the top-level components for each major view. For example, the [`Home`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/pages/Home.tsx#L5) component renders the primary chat interface, the [`Login`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/pages/Login.tsx#L16) component manages the authentication flow, and the [`Env`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/router.tsx#L6) component handles user-defined environment variables. A central [`Page`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/pages/Home.tsx#L1) component provides the overall layout, integrating structural elements like the header, left sidebar, and various content panels, while dynamically adapting its layout based on user configurations and active views.

All reusable UI components are housed within the [`frontend/src/components`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components) directory. This includes the core chat interface, which provides message display, user input ( [`MessageComposer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/chat/MessageComposer/index.tsx#L49)), and chat session management. It also features elements like the application header, chat settings modals, and dynamic rendering of rich message content such as images, videos, and interactive dataframes. The left sidebar, managed by components in [`frontend/src/components/LeftSidebar`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/LeftSidebar), offers thread history, search functionality, and thread management options.

Global state management is handled through Recoil atoms, defined in [`frontend/src/state`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state). These atoms manage various aspects of the UI, including file attachments, persistent chat commands, visibility of chat settings, and user environment variables, with some data persisted to local storage for user convenience.

Custom React hooks, found in [`frontend/src/hooks`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks), encapsulate complex logic for functionalities such as URL query parameter parsing, mobile viewport detection, command navigation, API data fetching, dynamic layout adjustments, and file upload management. These hooks promote code reusability and simplify component logic.

Internationalization support is configured in [`frontend/src/i18n`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/i18n), using [`react-i18next`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/package.json#L54) to manage language translations and ensure the UI can be localized.

The [`frontend/src/lib`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/lib) directory contains utility functions for various tasks, including pre-processing message content, embedding interactive elements, client-side routing, and general UI utility functions. Type definitions, centralized in [`frontend/src/types`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types), ensure consistency across the application for input components, chat session management, and message contexts.

The frontend uses [`frontend/postcss.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/postcss.config.js) and [`frontend/tailwind.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/tailwind.config.js) to configure its styling. Tailwind CSS is used to define a consistent design system with custom colors, animations, and dark mode support, leveraging CSS variables for themeability.

For additional information on the unified API client used for backend interactions, refer to [Backend API Client and Interaction Layer](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development-backend-api-client-and-interaction-layer). To understand the testing strategy for the frontend, refer to [Testing Strategy for Frontend Components](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development-testing-strategy-for-frontend-components).

### Frontend State Management with Recoil

link

zoom\_in

Global state management for the frontend is handled using Recoil.js, organizing data for various UI components and ensuring persistence across user sessions. Chat-related features, including active attachments and persistent commands, are managed through dedicated Recoil atoms. The [`IAttachment`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/chat.ts#L5) interface, defined in [`frontend/src/state/chat.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/chat.ts), structures attachment objects with properties such as ID, name, size, type, upload progress, and status. The [`attachmentsState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/chat.ts#L17) atom tracks these active attachments, while the [`persistentCommandState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/chat.ts#L22) atom manages a single active chat command.

Visibility of UI elements, such as the chat settings panel, is controlled by a boolean Recoil atom, [`chatSettingsOpenState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/project.ts#L3), located in [`frontend/src/state/project.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/project.ts). This atom defaults to [`false`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/.npmrc#L1), indicating the panel is closed by default.

User-specific environment variables are managed by the [`userEnvState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/user.ts#L5) atom, defined in [`frontend/src/state/user.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/state/user.ts). This atom stores key-value pairs representing user environment variables, initialized by attempting to retrieve and parse a JSON string from [`localStorage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts#L16). This mechanism ensures that user-defined variables persist across browser sessions.

The application dynamically renders a variety of rich message elements within the user interface, ranging from multimedia content like audio and video to complex data visualizations and interactive custom components. The primary component for this functionality, [`Element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L70), located at [`frontend/src/components/Elements/index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/Elements/index.tsx), acts as a central dispatcher. ### Custom React Hooks for Frontend Logic

link

The frontend of the application utilizes a set of custom React hooks to encapsulate and streamline common functionalities, promoting code reuse and modularity. These hooks abstract away complex logic, providing simple interfaces for components to interact with various aspects of the application.

For managing URL-based state, the [`useQuery`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks/query.ts#L4) hook, defined in [`frontend/src/hooks/query.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks/query.ts), provides a memoized [`URLSearchParams`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks/query.ts#L7) object. This allows components to easily access and parse query string parameters, such as user identifiers, without repeatedly processing the URL.

To enhance responsiveness across different devices, the [`useIsMobile`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks/use-mobile.tsx#L5) hook, located in [`frontend/src/hooks/use-mobile.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/hooks/use-mobile.tsx), dynamically detects if the current viewport width falls below a predefined mobile breakpoint. This enables components to render device-specific layouts or functionalities. ### Thread Sharing Functionality

link

zoom\_in

The system enables users to share and unshare chat threads, managing the user interface, API interactions, and state updates necessary to generate shareable links and reflect sharing statuses. The primary component facilitating this functionality is the [`ShareDialog`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/share/ShareDialog.tsx#L22) defined in [`frontend/src/components/share/ShareDialog.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/share/ShareDialog.tsx). This dialog allows users to create a public link for a private chat thread, enabling wider dissemination or collaboration.

When a user initiates a share action, the [`ShareDialog`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/share/ShareDialog.tsx#L22) interacts with the backend via API calls to mark the thread as shared. This operation updates the thread's metadata in the system's data layer. Concurrently, the frontend's global state, specifically the [`threadHistoryState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/state.ts#L192), is updated to reflect the new sharing status, ensuring that the UI consistently displays whether a thread is shared. The dialog then presents a shareable URL, which users can copy.

Conversely, the system also supports unsharing threads. When a thread is unshared, a similar process occurs: an API call is made to the backend to revoke the shared status, and the [`threadHistoryState`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/state.ts#L192) is updated to remove any associated shared metadata. This ensures that the previously generated share link becomes inactive.

User feedback for these operations, such as success or error messages, is provided through transient toast notifications. The system handles various scenarios, including cases where a thread is already shared, and ensures that the user interface remains responsive and accurate throughout the sharing and unsharing processes. The management of frontend state for shared threads is detailed in [Frontend State Management with Recoil](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development-frontend-state-management-with-recoil). Backend API interactions for these features are part of the [Backend API Client and Interaction Layer](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development-backend-api-client-and-interaction-layer).

This context provides a centralized mechanism for various components to access and update message-related properties without direct prop drilling, facilitating consistent behavior across the user interface.

The [`MessageContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/contexts/MessageContext.tsx#L17) encapsulates several key pieces of information and functionality:

- **Highlighted Message**: Tracks a currently highlighted message, allowing for visual emphasis or specific interactions with that message.
- **Loading State**: Indicates whether messages are in a loading state, which can be used to display loading indicators to the user.
- **Editability**: Determines if messages are editable, controlling the user's ability to modify message content.
- **Element Reference Clicks**: Provides a callback ( [`onElementRefClick`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/messageContext.ts#L22)) that is triggered when a user interacts with an element reference within a message. - **Feedback Updates**: Offers a callback ( [`onFeedbackUpdated`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/messageContext.ts#L23)) to handle updates to user feedback on messages, allowing the UI to react to changes in feedback status.
- **Feedback Button Visibility**: Controls the display of feedback buttons (e.g., "thumbs up," "thumbs down") on messages.
- **Error Handling**: Includes a function ( [`onError`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/index.tsx#L51)) for managing errors related to message interactions.
- **UI Name**: A string that can identify the specific UI context or component interacting with the message.
- **Chain of Thought (COT)**: A property ( [`cot`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/config.py#L324)) that can control the visibility of a "Chain of Thought" feature, likely for debugging or advanced AI interactions.

The context is initialized with default values, and its structure is defined by the [`IMessageContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/messageContext.ts#L9) type, ensuring type consistency across components that consume this context. This approach simplifies the management of complex message interactions and their corresponding UI updates throughout the frontend application.

The [`IMessageContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/messageContext.ts#L9) interface, located in [`frontend/src/types/messageContext.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/messageContext.ts), outlines the data and functions available within a message's UI context. This includes functionalities for file uploads, chain of thought display modes, user prompts, message editability, and feedback mechanisms. This context integrates with external types from the [`@chainlit/react-client`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L69) library, emphasizing its role within the broader Chainlit frontend.

All these type definitions are aggregated and re-exported through [`frontend/src/types/index.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/types/index.ts), creating a single, convenient point of access for consuming modules.

Chainlit's user interfaces are constructed using a set of reusable React-based components and utilities. It provides global functions for lifecycle management, such as [`mountChainlitWidget`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L30) and [`unmountChainlitWidget`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L31) from [`libs/copilot/index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx), which handle the dynamic creation and removal of the widget. Global interaction functions like [`toggleChainlitCopilot`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L567) and [`sendChainlitMessage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L33) allow external control over the embedded interface. The widget incorporates its own chat interface, state management, and theming, ensuring a consistent user experience regardless of the embedding environment.

For building React applications that integrate directly with a Chainlit backend, the [`@chainlit/react-client`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L69) library, located in [`libs/react-client`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client), offers a suite of React hooks and an API client. This library streamlines common functionalities such as managing chat sessions, messages, and real-time interactions, including audio processing. Components within this library use Recoil for global state management, centralizing the handling of conversational history, UI elements, and user input. This client library provides robust API communication capabilities, including authentication and structured interaction with backend resources.

Theming across Chainlit's UI components is managed dynamically, allowing for persistence of user preferences and consistent visual design. Styling methodologies leverage PostCSS and Tailwind CSS, as configured in [`libs/copilot/postcss.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/postcss.config.js) and [`libs/copilot/tailwind.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/tailwind.config.js) respectively. A dedicated CSS file, [`libs/copilot/sonner.css`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/sonner.css), defines detailed styling for toast notifications, encompassing positioning, appearance, theming, and animations.

The development and testing of these reusable UI components are supported by Storybook, configured within [`libs/copilot/.storybook`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/.storybook). Storybook provides a dedicated environment for documenting and visually testing components in isolation, defining various component stories in [`libs/copilot/stories`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/stories) to demonstrate their behavior under different configurations.

The React client library also includes extensive type definitions in [`libs/react-client/src/types`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/types), ensuring type consistency across data models for actions, elements, messages, and user interactions. Utility functions for pre-processing messages, managing client-side routing, and other common frontend tasks are provided in [`frontend/src/lib`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/lib).

### Chainlit Copilot Widget: Embedding and Lifecycle

link

zoom\_in

The Chainlit Copilot widget is a React-based application designed for embedding into any webpage, providing an interactive chat interface. Its architecture emphasizes isolation from the host environment through the use of a Shadow DOM, ensuring that its styles and scripts do not interfere with the embedding page. Global JavaScript functions are exposed to allow the host page to control the widget's lifecycle and interactions.

The primary mechanism for embedding the widget is the [`mountChainlitWidget`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L30) function, defined in [`libs/copilot/index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx). This function dynamically creates a container [`div`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L168) element, attaches an open Shadow DOM to it, and then renders the main [`AppWrapper`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/AppWrapper.tsx#L13) React component within this isolated environment. To maintain style encapsulation, inline CSS content from libraries like Tailwind CSS, Sonner, and Highlight.js is injected directly into the Shadow DOM, guaranteeing that these styles are scoped exclusively to the widget.

Lifecycle management for the widget is also handled through global functions. [`mountChainlitWidget`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L30) initializes and embeds the widget, while [`unmountChainlitWidget`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L31) provides a clean way to remove the widget from the DOM and unmount its React application, releasing associated resources. For dynamic interaction, [`toggleChainlitCopilot`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L567), [`sendChainlitMessage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L33), [`getChainlitCopilotThreadId`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts#L50), and [`clearChainlitCopilotThreadId`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts#L55) are made available on the global [`window`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/App.tsx#L17) object. These functions enable the host page to control the widget's visibility, send messages to the copilot, and manage its unique conversation thread identifier, which ensures session continuity. The thread ID itself is managed using Recoil's state management, with persistence in [`localStorage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts#L16), as detailed in [`libs/copilot/src/state.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts).

The widget's configuration, such as the Chainlit server URL, access tokens, and theming preferences, is passed via an [`IWidgetConfig`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/types.ts#L1) object, which is defined in [`libs/copilot/src/types.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/types.ts). This configuration allows for customization of the widget's behavior and appearance upon embedding. The [`AppWrapper`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/AppWrapper.tsx#L13) component in [`libs/copilot/src/appWrapper.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/appWrapper.tsx) utilizes this configuration to initialize the API client, handle custom theme loading, and set up the global state. The [`App`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/App.tsx#L27) component, located in [`libs/copilot/src/app.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/app.tsx), further manages authentication, internationalization, and applies the specified theme, making use of [`window.cl_shadowRootElement`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L49) for dynamic style application. The theming system, explained in [Theming and Styling Methodologies](https://codewiki.google/github.com/chainlit/chainlit#reusable-ui-components-and-react-integration-theming-and-styling-methodologies), allows for dynamic theme application and persistence of user preferences within the Shadow DOM.

### React Client Library: Hooks and API

link

zoom\_in

The [`@chainlit/react-client`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L69) library provides a set of React hooks and an API client for connecting a React application to a Chainlit backend. It manages chat sessions, messages, and interactions, including real-time updates and audio processing, simplifying the creation of interactive chat interfaces within any React project.

The architecture uses Recoil for global state management. Applications should be wrapped in a [`RecoilRoot`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/main.tsx#L5) to enable access to shared state across components. The [`ChainlitContext.Provider`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/main.tsx#L17) makes an instance of [`ChainlitAPI`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/index.tsx#L174) available throughout the component tree, which facilitates communication with the backend.

The [`ChainlitAPI`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/index.tsx#L174) class, defined in [`libs/react-client/src/api/index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/index.tsx), handles HTTP requests, authentication, and interactions with backend resources like thread management, element updates, and Multi-Client Protocol (MCP) connections. It includes error handling mechanisms, consistent with [`ClientError`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/index.tsx#L24).

React hooks streamline client-side interactions and data management:

- [`useChatSession`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatSession.ts#L58) (from [`libs/react-client/src/useChatSession.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatSession.ts)) manages the WebSocket connection, handling session lifecycle events and processing real-time data from the server, such as new messages, message updates, and streaming tokens. It also coordinates audio input and output via [`WavRecorder`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/wavtools/wav_recorder.js#L18) and [`WavStreamPlayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/wavtools/wav_stream_player.js#L8) utilities.
- [`useChatMessages`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatMessages.ts#L9) (from [`libs/react-client/src/useChatMessages.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatMessages.ts)) provides access to the conversation history, including messages and the initial user interaction.
- [`useChatData`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatData.ts#L23) (from [`libs/react-client/src/useChatData.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatData.ts)) offers a consolidated view of various chat-related states and data, such as available actions, user prompts, avatars, chat settings, and connection status.
- [`useChatInteract`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatInteract.ts#L28) (from [`libs/react-client/src/useChatInteract.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useChatInteract.ts)) provides functions for client-side chat interactions, including [`sendMessage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/README.md?plain=1#L147), managing audio streams, updating chat settings, and clearing session data. These interactions communicate with the backend primarily through WebSockets.
- [`useAudio`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useAudio.ts#L12) (from [`libs/react-client/src/useAudio.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/useAudio.ts)) manages the state and control of audio conversations, encompassing the initiation and termination of audio streams, and the recording and playback of WAV data.

Type definitions, located in [`libs/react-client/src/types`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/types), provide a structured schema for client-side data models, ensuring type safety and consistency across various components and functionalities, including actions, commands, UI elements, conversational steps, and user management.

Utilities, found in [`libs/react-client/src/utils`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/utils), support data organization and manipulation. The library also includes WAV tools in [`libs/react-client/src/wavtools`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/wavtools) for audio processing. These tools handle audio analysis, WAV packing, recording from microphones, and streaming playback, often utilizing the Web Audio API for real-time operations and visualization. This enables features such as audio frequency visualization, conversion of raw audio data to WAV format, and real-time audio input/output.

### Theming and Styling Methodologies

link

zoom\_in

Chainlit UI components incorporate a theming system that supports dynamic application of themes, persistence of user preferences, and a consistent visual design. This system leverages PostCSS and Tailwind CSS for styling, with particular attention to encapsulating styles within a Shadow DOM for embedded components.

The core of the theming system is implemented by the [`ThemeProvider`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/ThemeProvider.tsx#L38) component, located at [`frontend/src/components/ThemeProvider.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/components/ThemeProvider.tsx) and duplicated in [`libs/copilot/src/ThemeProvider.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/ThemeProvider.tsx) for the copilot widget. This provider manages the current theme state, which can be 'dark', 'light', or 'system'. When set to 'system', the theme dynamically adapts to the user's operating system preference. User theme selections are persisted in [`localStorage`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/state.ts#L16) to ensure consistency across sessions. The [`ThemeProvider`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/ThemeProvider.tsx#L38) dynamically applies CSS classes, such as [`dark`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/types.py#L287) or [`light`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/src/lib/utils.ts#L31), to the document's root element or a dedicated Shadow DOM container ( [`window.cl_shadowRootElement`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L49) for the copilot widget), and injects custom CSS variables based on the active theme. This approach allows for global theme switching by simply changing class names and CSS variable values. The [`useTheme`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/ThemeProvider.tsx#L105) hook provides a convenient way for components to access the current theme and a function to update it.

The styling methodology relies on PostCSS and Tailwind CSS. The PostCSS configuration, found at [`libs/copilot/postcss.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/postcss.config.js), configures PostCSS to use [`tailwindcss`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/package.json#L71) and [`autoprefixer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/package.json#L91) plugins. This setup enables developers to write CSS using Tailwind's utility-first classes while ensuring cross-browser compatibility. Tailwind's configuration, specified in [`libs/copilot/tailwind.config.js`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/tailwind.config.js), extends the default theme with custom colors, border radii, keyframes, and animations. These custom definitions, often based on HSL values and CSS variables, facilitate dynamic theming.

For embedded components like the Chainlit Copilot widget, styling is encapsulated within a Shadow DOM. The [`index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/vite.config.ts#L13) file at [`libs/copilot/index.tsx`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx) is responsible for mounting the widget and injecting necessary CSS, including [`tailwindcss`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/frontend/package.json#L71), [`sonnercss`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L7), and [`hljscss`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/index.tsx#L11), directly into the Shadow DOM. This ensures that the widget's styles are isolated from the host page, preventing conflicts. The [`libs/copilot/sonner.css`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/sonner.css) file provides detailed styling for a toast notification system, defining appearance, positioning, and animation, with support for both light and dark themes and right-to-left languages. Base styles and theme variables for the Shadow DOM are defined in [`libs/copilot/src/index.css`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/index.css), targeting specific container IDs like [`#cl-shadow-root`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/src/index.css#L5) to ensure style encapsulation and adherence to the theming system.

The configuration in [`libs/copilot/.storybook/main.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/.storybook/main.ts) and [`libs/copilot/.storybook/preview.ts`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/copilot/.storybook/preview.ts) sets up Storybook for React/Vite projects, integrating addons for various functionalities and ensuring global styles are applied within the preview environment. ## Application Lifecycle and Configuration

link

zoom\_in

Chainlit applications are initiated, configured, and managed primarily through a command-line interface (CLI). This CLI, built using [`click`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/RELENG.md?plain=1#L30), serves as the central point for developers to run and interact with their conversational AI applications. It handles the parsing of command-line arguments and the orchestration of the backend server, typically powered by [`uvicorn`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L516).

The lifecycle of a Chainlit application begins with the [`chainlit run`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) command, which is responsible for launching the server. This command allows for various configurations, such as specifying the user's application module, enabling live reloading ( [`watch`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/config.py#L238) mode), running in a [`headless`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/config.py#L237) state, or setting debug logging. It also facilitates secure communication by supporting SSL certificate and key configurations. During startup, the CLI ensures that essential components, such as [`JWT`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/__init__.py#L24) secrets for authentication, are present and initializes features like LangChain caches. A crucial validation step confirms that the user's application module defines at least one core callback (e.g., [`on_chat_start`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L45), [`on_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L51), or [`on_audio_chunk`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/callbacks.py#L307)) to ensure basic conversational functionality.

Configuration management is a key aspect of the application lifecycle. The CLI integrates with environment variables (e.g., [`CHAINLIT_HOST`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1643), [`UVICORN_WS_PER_MESSAGE_DEFLATE`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1223)) and command-line options, with the latter often taking precedence. This flexible approach allows for easy adaptation to different deployment environments. Beyond running applications, the CLI also provides utilities for initial setup, such as [`chainlit init`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) to create a default configuration and [`chainlit create-secret`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) to generate secure [`JWT`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/__init__.py#L24) secrets. For a detailed breakdown of the available commands and their usage, refer to [Command-Line Interface (CLI) for Application Management](https://codewiki.google/github.com/chainlit/chainlit#application-lifecycle-and-configuration-command-line-interface-cli-for-application-management).

### Command-Line Interface (CLI) for Application Management

link

zoom\_in

The Chainlit Command-Line Interface (CLI) provides the primary means for users to interact with and manage their Chainlit applications. Built on [`click`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/RELENG.md?plain=1#L30), the CLI facilitates tasks such as launching the application, configuring its behavior, and performing various utility functions.

The central command, [`chainlit run`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3), is responsible for initiating the Chainlit server. This command handles the dynamic loading of the user's application module, orchestrates server setup, and can be configured with options for live reloading ( [`watch`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/config.py#L238)), headless operation, debug logging, and caching behavior. It also supports secure socket layer (SSL) configuration for secure communication. A core function of the server startup process is to ensure the presence of a JSON Web Token (JWT) secret, which is critical for authentication within the application. The CLI also includes a validation step to ensure that the user's application defines essential callbacks, such as [`on_chat_start`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L45), [`on_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L51), or [`on_audio_chunk`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/callbacks.py#L307), before the server starts, ensuring the application has core conversational capabilities. This ensures a functional foundation for subsequent interactions.

Beyond application execution, the CLI offers commands for initial setup and maintenance. The [`chainlit init`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) command aids in setting up the basic Chainlit configuration, potentially creating a default configuration file. For secure authentication, [`chainlit create-secret`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) generates a random JWT secret, prompting the user to integrate it into their environment. Additionally, [`chainlit lint-translations`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L3) provides a utility for checking translation files, supporting the frontend's internationalization efforts, as further described in [Frontend Internationalization (i18n)](https://codewiki.google/github.com/chainlit/chainlit#frontend-application-development-frontend-internationalization-i18n). The CLI leverages both environment variables and command-line options for flexible configuration, with command-line options typically taking precedence. The [`nest_asyncio.apply()`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/cli/__init__.py#L8) call, made at the module level in [`backend/chainlit/cli/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/cli/__init__.py), allows for nested asynchronous event loops, a design consideration for managing concurrent asynchronous operations.

## User Authentication and Authorization

link

zoom\_in

User authentication and authorization within Chainlit applications involve managing user sessions, handling JSON Web Tokens (JWTs), and integrating with various OAuth providers. The system determines whether a login is required based on configured authentication methods, including custom authentication, password authentication, header authentication, or OAuth enablement.

The core authentication logic resides in [`backend/chainlit/auth`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth). This module orchestrates the authentication process by managing configuration, user authentication, and token handling. It also provides utilities for creating and decoding JWTs and ensures the presence of a JWT secret.

JWTs are fundamental for secure, token-based authentication. The [`backend/chainlit/auth/jwt.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py) module is responsible for encoding user information into a JWT and decoding it back into a [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object. A secret key, retrieved from the [`CHAINLIT_AUTH_SECRET`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L10) environment variable, is used for signing and verifying these tokens. This secret is critical for the security of the JWTs, ensuring their integrity and authenticity. When a user authenticates, their [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object is encoded into a JWT, which includes an expiration time and an issued-at time. Conversely, [`decode_jwt`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py#L31) verifies the token's signature and reconstructs the [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object.

User session management largely relies on cookie-based authentication, implemented in [`backend/chainlit/auth/cookie.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/cookie.py). This module handles setting, retrieving, and clearing authentication and OAuth state cookies. It employs a custom [`OAuth2PasswordBearerWithCookie`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/cookie.py#L35) security scheme that prioritizes token retrieval from cookies but can fall back to standard [`Bearer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/mcp.py#L55) token authorization headers if cookies are not present. To address browser size limitations for individual cookies, the system uses chunked cookies, splitting large tokens into multiple smaller parts for storage. All sensitive cookies are marked as [`httponly=True`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L771) to prevent client-side JavaScript access and are configured with appropriate [`secure`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1581) and [`samesite`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1197) attributes for enhanced security. Additionally, this module manages OAuth state cookies, which are used to maintain state during the OAuth authentication flow.

The authentication system also integrates with a data layer to manage persistent user data, obtained via [`get_data_layer()`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L616). When a user is authenticated, the system can retrieve or create a persistent user entry and update their display name if available. This ensures that user information is consistently managed across sessions. The overall authentication configuration, including login requirements and enabled providers, is determined by environment variables and Chainlit's internal configuration.

### JWT-based Authentication and Secret Management

link

zoom\_in

JSON Web Tokens (JWTs) are fundamental for secure authentication within Chainlit, providing a method to verify user identity without repeated credential submissions. The core process involves encoding user information into a JWT and subsequently decoding and verifying it upon receipt. This system relies heavily on a secret key, designated [`CHAINLIT_AUTH_SECRET`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L10), which is crucial for digitally signing and validating the tokens. The [`HS256`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py#L27) cryptographic algorithm is employed for these signing and verification operations.

The creation of a JWT, handled by the [`create_jwt`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py#L15) function in [`backend/chainlit/auth/jwt.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py), involves serializing a [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object into a token. This token includes claims such as [`exp`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/libs/react-client/src/api/hooks/auth/types.ts#L4) (expiration time) and [`iat`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py#L21) (issued at time), with the expiration configured based on the project's user session timeout. Conversely, the [`decode_jwt`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py#L31) function in [`backend/chainlit/auth/jwt.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/jwt.py) performs the reverse, verifying the token's signature using the [`CHAINLIT_AUTH_SECRET`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/cypress/e2e/auth/main.py#L10) and reconstructing the [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) object. The presence of this secret is enforced, and its absence will prevent the system from operating, underscoring its necessity for secure authentication.

For a broader understanding of how these JWTs integrate into the overall authentication flow, including OAuth and cookie management, refer to the [User Authentication and Authorization](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization) section, and specifically [Cookie-based Session Management](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization-cookie-based-session-management) for details on session handling.

### Cookie-based Session Management

link

zoom\_in

User session management within Chainlit applications relies on HTTP cookies, which provide a mechanism for maintaining state across requests. This is primarily handled by the [`OAuth2PasswordBearerWithCookie`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/auth/cookie.py#L35) class, which is designed to extract authentication tokens from incoming requests. This class first attempts to retrieve tokens from cookies. If no token is found in the cookies, it then checks the [`Authorization`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/mcp.py#L55) header, providing flexibility for different client types.

To address browser limitations on cookie size, the system employs a strategy of chunked cookies. When an authentication token exceeds a predefined size limit, it is automatically split into multiple smaller cookies. These individual chunks are then stored by the client and reassembled by the server upon subsequent requests, effectively bypassing size constraints without compromising the integrity of the token. Conversely, when an authentication cookie is set in the response, any previously set cookie chunks are automatically cleared to prevent stale or orphaned data.

For OAuth-based authentication flows, the system also manages an OAuth state cookie. This cookie is used to store and validate the state parameter, which is a security measure designed to mitigate Cross-Site Request Forgery (CSRF) attacks during the OAuth authorization process. The state cookie is set when an OAuth flow is initiated and validated upon the callback, ensuring that the response matches the original request. After validation, the OAuth state cookie is cleared to maintain security and prevent replay attacks. All sensitive cookies, including those for authentication and OAuth state, are configured with the [`httponly=True`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L771) attribute, which prevents client-side JavaScript from accessing them, thereby reducing the risk of cross-site scripting (XSS) vulnerabilities. Additionally, the [`secure`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1581) attribute is dynamically set based on the deployment environment to ensure cookies are only transmitted over encrypted connections when appropriate. For further details on JWT creation and decoding, refer to [JWT-based Authentication and Secret Management](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization-jwt-based-authentication-and-secret-management).

## Data Persistence and Storage

link

zoom\_in

Chainlit's data persistence and storage system is designed to offer a unified interface for handling application data across various backends. This system allows for flexible configuration of different database and object storage solutions through environment variables or custom settings. The core architecture centers around the [`BaseDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L20) abstract class, defined in [`backend/chainlit/data/base.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py), which establishes a consistent asynchronous API for managing users, feedback, UI elements, conversational steps, and threads.

A singleton pattern ensures that only one data layer instance is active at any given time, managed by the [`get_data_layer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L14) function in [`backend/chainlit/data/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py). This function determines the appropriate data layer implementation based on a precedence order: a custom data layer provided by the user, followed by [`ChainlitDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/chainlit_data_layer.py#L40) if a [`DATABASE_URL`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L32) is set (typically for PostgreSQL), and then [`LiteralDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/literalai.py#L220) if [`LITERAL_API_KEY`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L35) is configured (though this integration is being deprecated). Additionally, [`DynamoDBDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py#L43) in [`backend/chainlit/data/dynamodb.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py) provides an implementation for AWS DynamoDB, and [`SQLAlchemyDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py#L37) in [`backend/chainlit/data/sql_alchemy.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py) supports SQL-based databases using SQLAlchemy.

Many operations within these data layers, such as creating or updating elements and steps, are designed to be deferred until the first user message is received. This optimization, facilitated by the [`queue_until_user_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py#L8) decorator in [`backend/chainlit/data/utils.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py), aims to improve initial loading performance and maintain data consistency within conversational flows.

For handling non-textual data, such as files associated with UI elements, Chainlit employs a modular object storage system. The [`BaseStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/base.py#L8) abstract class, located in [`backend/chainlit/data/storage_clients/base.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/base.py), defines a common interface for file upload, deletion, and read URL generation. Specific implementations are available for various cloud storage providers, including [`AzureStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure.py#L21) for Azure Data Lake Storage in [`backend/chainlit/data/storage_clients/azure.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure.py), [`AzureBlobStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure_blob.py#L11) for Azure Blob Storage in [`backend/chainlit/data/storage_clients/azure_blob.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure_blob.py), [`GCSStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/gcs.py#L12) for Google Cloud Storage in [`backend/chainlit/data/storage_clients/gcs.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/gcs.py), and [`S3StorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/s3.py#L11) for Amazon S3 in [`backend/chainlit/data/storage_clients/s3.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/s3.py). These clients handle authentication and interactions with their respective cloud services, abstracting the underlying complexity.

Access control for conversational threads is managed by the [`is_thread_author`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/acl.py#L6) function in [`backend/chainlit/data/acl.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/acl.py), which verifies if a user is authorized to access a specific thread, raising HTTP exceptions for unauthorized attempts.

### Unified Data Layer Interface and Implementations

link

zoom\_in

The data persistence layer in Chainlit is built around the [`BaseDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L20) abstract interface, defined in [`backend/chainlit/data/base.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py). This interface standardizes how the application interacts with various storage backends for core data entities such as users, conversational threads, individual steps within a conversation, UI elements associated with these steps, and user feedback. This abstraction allows Chainlit to support multiple underlying databases and object storage solutions without altering the application's core logic.

The [`get_data_layer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L14) function in [`backend/chainlit/data/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py) is responsible for initializing and providing a singleton instance of the appropriate data layer implementation based on the application's configuration. This selection process prioritizes custom user-defined data layers, followed by those configured via environment variables like [`DATABASE_URL`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L32) (for relational databases) or [`LITERAL_API_KEY`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/__init__.py#L35) (for integration with LiteralAI).

Chainlit offers several concrete implementations of the [`BaseDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L20) interface:

- **[`ChainlitDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/chainlit_data_layer.py#L40)**: Located in [`backend/chainlit/data/chainlit_data_layer.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/chainlit_data_layer.py), this implementation primarily uses [`asyncpg`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/pyproject.toml#L100) for PostgreSQL databases. It integrates with various object storage clients, such as Amazon S3, Google Cloud Storage, and Azure Blob Storage, to handle file uploads and retrieval associated with UI elements. It manages CRUD operations for Chainlit entities and supports advanced querying and pagination.
- **[`LiteralDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/literalai.py#L220)**: Defined in [`backend/chainlit/data/literalai.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/literalai.py), this layer integrates with the LiteralAI platform for data persistence. It handles the conversion of data structures between LiteralAI's format and Chainlit's internal models, managing users, threads, steps, elements, and feedback within the LiteralAI backend. A deprecation warning is present, indicating its future removal.
- **[`DynamoDBDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py#L43)**: Found in [`backend/chainlit/data/dynamodb.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py), this implementation uses AWS DynamoDB. It handles the specific serialization and deserialization requirements for DynamoDB data types and supports thread querying with pagination using a single-table design pattern and Global Secondary Indexes (GSIs). It also integrates with a storage provider for file uploads and downloads.
- **[`SQLAlchemyDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py#L37)**: In [`backend/chainlit/data/sql_alchemy.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py), this layer provides a SQL-based persistence mechanism leveraging SQLAlchemy. It uses an [`AsyncEngine`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py#L12) for asynchronous operations and employs an upsert pattern for many data modifications. It manages users, threads, steps, feedback, and elements, serializing complex fields like metadata and generation data as JSON.

Many data layer operations, particularly those related to creating or updating elements and steps, are decorated with [`queue_until_user_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py#L8) from [`backend/chainlit/data/utils.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py). This decorator defers the execution of these operations until the first user message is received within a WebSocket session. This design choice aims to optimize initial application loading and ensure data consistency during conversational flows.

For detailed information on how files are managed across these data layers, refer to [Object Storage Clients for Elements](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage-object-storage-clients-for-elements). The access control mechanisms for threads are handled by the [`is_thread_author`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/acl.py#L6) function, which verifies user authorization against the data layer to ensure that users can only access threads they own or are authorized for, as described in [`backend/chainlit/data/acl.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/acl.py).

### Object Storage Clients for Elements

link

zoom\_in

The object storage clients provide a modular architecture for handling file uploads, deletions, and the generation of read URLs across various cloud storage providers. This design is built around a [`BaseStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/base.py#L8) abstract class, which defines a consistent interface for these operations, allowing the system to interact with different storage backends uniformly.

Specific implementations of [`BaseStorageClient`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/base.py#L8) are provided for major cloud services:

- Azure Data Lake Storage (ADLS) Gen2, implemented in [`backend/chainlit/data/storage_clients/azure.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure.py), enables file management within ADLS file systems.
- Azure Blob Storage, implemented in [`backend/chainlit/data/storage_clients/azure_blob.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/azure_blob.py), focuses on managing blob objects and generating Shared Access Signature (SAS) URLs for secure access.
- Google Cloud Storage (GCS), implemented in [`backend/chainlit/data/storage_clients/gcs.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/gcs.py), integrates with GCS buckets, supporting various authentication methods and both synchronous and asynchronous operations.
- Amazon S3, implemented in [`backend/chainlit/data/storage_clients/s3.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/s3.py), uses the [`boto3`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/pyproject.toml#L96) library to interact with S3 buckets for object storage.

Each client handles the specifics of its respective cloud provider, such as authentication, content settings, and URL generation mechanisms (e.g., SAS tokens for Azure, pre-signed URLs for S3 and GCS). The [`storage_expiry_time`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/storage_clients/base.py#L5) environment variable is generally used to control the expiration time for generated read URLs, enhancing security by limiting access duration. The system ensures that both synchronous and asynchronous versions of key operations are available where applicable, supporting non-blocking I/O in asynchronous application contexts.

### Deferred Operations with queue\_until\_user\_message

link

zoom\_in

The [`queue_until_user_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py#L8) decorator plays a significant role in managing data layer operations, particularly for optimizing initial application loading and maintaining data consistency within conversational flows. This decorator, defined in [`backend/chainlit/data/utils.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py), defers the execution of certain asynchronous methods until the first user message is received in a [`WebsocketSession`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/session.py#L203).

When a method decorated with [`queue_until_user_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/utils.py#L8) is invoked, the system checks if a user has already initiated interaction. If not, the method call, including its arguments, is enqueued. This queue is then processed only after the [`context.session.has_first_interaction`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/server.py#L1251) flag becomes [`True`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L89), which typically occurs upon receipt of the initial user message. If a user has already interacted, the method executes immediately.

This deferred execution strategy is applied to several key data layer operations across various implementations of the [`BaseDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L20). For instance, in the [`ChainlitDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/chainlit_data_layer.py#L40) ( [`backend/chainlit/data/chainlit_data_layer.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/chainlit_data_layer.py)), [`create_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L47), [`delete_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L58), [`create_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/base.py#L63), [`update_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L81), and [`delete_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L85) are all subject to this queuing mechanism. Similar patterns are observed in [`DynamoDBDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py#L43) ( [`backend/chainlit/data/dynamodb.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/dynamodb.py)) and [`SQLAlchemyDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py#L37) ( [`backend/chainlit/data/sql_alchemy.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/sql_alchemy.py)), where operations involving the creation, updating, or deletion of elements and steps are likewise decorated. The [`LiteralDataLayer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/literalai.py#L220) ( [`backend/chainlit/data/literalai.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/data/literalai.py)) also utilizes this decorator for similar operations.

The motivation behind this design is to prevent unnecessary database writes or operations during the initial setup or inactive periods of a conversational session. By deferring these actions, the system can improve responsiveness during application startup and ensure that data modifications are synchronized with actual user engagement, thereby enhancing overall efficiency and data integrity.

## Real-time Communication and API Endpoints

link

zoom\_in

Chainlit applications manage real-time communication between the backend and the user interface using a WebSocket connection and expose core functionalities through various API endpoints. The emitter also supports streaming individual tokens for real-time AI responses via [`send_token`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L133) and displays temporary notifications using [`send_toast`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L149). More details on how this emitter operates can be found in [`backend/chainlit/emitter.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py).

These API endpoints are secured and integrated with various authentication mechanisms, including JWT-based authentication and OAuth providers, as described in [User Authentication and Authorization](https://codewiki.google/github.com/chainlit/chainlit#user-authentication-and-authorization). The core component responsible for managing this real-time event flow is the [`ChainlitEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L154), which is instantiated within the [`ChainlitContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/context.py#L23) (see [Core Backend Architecture and Event Handling](https://codewiki.google/github.com/chainlit/chainlit#core-conversational-ai-application-core-backend-architecture-and-event-handling)). The [`ChainlitEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L154) facilitates the bidirectional exchange of information, sending various event-driven data from the backend to the connected frontend client. These events include new messages, updates to conversational steps, display of UI elements (such as images, text, and interactive components), and notifications. The [`ChainlitEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L154) also handles interactive elements where the backend needs to await a user response. This ensures that each user interaction maintains its state and can effectively communicate with the backend. The [`ChainlitEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L154) also processes incoming user messages, managing their persistence and handling any associated file references. Upon the first user interaction, it initializes or updates the thread, ensuring a coherent conversational flow.

Chainlit integrates with various AI frameworks, including LangChain, LlamaIndex, and OpenAI, to provide enhanced observability and debugging capabilities for AI model operations. For LangChain, the [`LangchainTracer`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/langchain/callbacks.py#L317) in [`backend/chainlit/langchain/callbacks.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/langchain/callbacks.py) acts as a custom callback handler. This tracer manages the streaming of final answers and organizes run data, providing detailed metrics for LLM generations including token counts and time-to-first-token. It also includes logic to filter which LangChain runs are converted into Chainlit steps, optimizing the visual display of complex applications.

The integration with LlamaIndex, handled by the [`LlamaIndexCallbackHandler`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/llama_index/callbacks.py#L23) in [`backend/chainlit/llama_index/callbacks.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/llama_index/callbacks.py), processes LlamaIndex callback events and converts them into Chainlit UI elements. It initializes and updates Chainlit [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) objects for various LlamaIndex events, categorizing them appropriately (e.g., as "tool" or "llm" steps). For query and retrieval events, it extracts and displays source nodes in the Chainlit side panel, while for LLM events, it provides structured [`ChatGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) or [`CompletionGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) objects with details like message history, prompts, and token counts. Asynchronous updates ensure that the UI remains responsive without blocking LlamaIndex execution.

For OpenAI API calls, Chainlit provides automatic instrumentation for LLM observability. The [`instrument_openai`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/openai/__init__.py#L11) function in [`backend/chainlit/openai/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/openai/__init__.py) hooks into OpenAI generation events. It creates and sends [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) objects for each [`ChatGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) or [`CompletionGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125), populated with details such as the model, provider, input, output, and timing. These steps are sent asynchronously to the Chainlit backend, ensuring that tracking does not interfere with the performance of OpenAI API calls. The system also enforces version compatibility for the OpenAI library to prevent integration issues.

### LlamaIndex Callback Handling for UI Visualization

link

zoom\_in

The integration between Chainlit and LlamaIndex enhances observability by converting LlamaIndex operations into interactive elements within the Chainlit user interface. This handler processes various LlamaIndex events, such as queries, retrievals, and calls to Language Model Models (LLMs), and transforms them into Chainlit [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) objects.

When a LlamaIndex event begins, a new Chainlit [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) is initiated, capturing details like the event type, associated payload, and any metadata. This [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) is then updated as the LlamaIndex event progresses. For example, during a query or retrieval event, the handler extracts source nodes, which are then presented as [`Text`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L266) elements in the Chainlit UI, often displayed in a side panel for detailed review. Similarly, for LLM-related events, the handler processes messages, prompts, and responses to create structured [`ChatGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) or [`CompletionGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) objects. These objects include model information, conversational history, prompt content, and token usage, providing a comprehensive view of the LLM's operation.

The system ensures that Chainlit [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) updates occur asynchronously, preventing any blocking of the LlamaIndex execution and maintaining a responsive user interface. To visualize the flow of operations, a parent-child relationship is established between steps, enabling a nested and structured view of complex interactions. This integration also includes a check for the minimum required version of LlamaIndex via [`backend/chainlit/llama_index/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/llama_index/__init__.py) to ensure compatibility. This approach allows developers to effectively visualize and debug the internal workings of their LlamaIndex applications directly within the Chainlit environment. For additional details on AI framework integrations, refer to [AI Framework Integrations and Observability](https://codewiki.google/github.com/chainlit/chainlit#ai-framework-integrations-and-observability).

### OpenAI API Instrumentation for LLM Tracking

link

zoom\_in

Chainlit integrates with the OpenAI API to provide observability for Large Language Model (LLM) interactions. This integration automatically tracks OpenAI API calls, specifically those involving [`ChatGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) and [`CompletionGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125), and converts them into Chainlit [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) objects for visualization and debugging within the Chainlit user interface.

The core of this functionality is managed by the [`instrument_openai`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/openai/__init__.py#L11) function, found in [`backend/chainlit/openai/__init__.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/openai/__init__.py). When activated, typically during application startup, this function sets up an instrumentation callback that intercepts OpenAI generation events. Upon detection of a new [`ChatGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125) or [`CompletionGeneration`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/CHANGELOG.md?plain=1#L1125), the callback creates a [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) object. This [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) object encapsulates details such as the model or provider used, the type of operation (designated as "llm"), and the input and output content of the generation. It also records the start and end times of the generation, ensuring accurate timing information.

These [`Step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L164) objects are then asynchronously sent to the Chainlit server, preventing the tracking mechanism from impeding the performance of the main application. This asynchronous approach ensures that the observability features operate efficiently without introducing significant latency to the LLM interactions. The integration also supports hierarchical step tracking, allowing OpenAI generations to be contextualized within a broader conversation flow, thereby enriching the observability data presented in the Chainlit UI.

A [`DiscordEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L59) is also configured, which is responsible for translating Chainlit-specific events and messages into Discord-compatible formats for real-time communication. This emitter handles the display of elements and messages within Discord channels. For a deeper understanding of real-time communication, refer to [Real-time Communication with WebSockets](https://codewiki.google/github.com/chainlit/chainlit#real-time-communication-and-api-endpoints-real-time-communication-with-websockets).

User identification and persistence are central to the integration. When a Discord user interacts with the bot, the system identifies them using Chainlit's [`User`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L29) and [`PersistedUser`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/user.py#L42) models. This process involves retrieving existing user information or creating new user profiles as needed, and caching them to maintain continuity across sessions. The system leverages Chainlit's data layer to persist user and thread information, providing a consistent experience. More details on the data layer can be found in [Unified Data Layer Interface and Implementations](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage-unified-data-layer-interface-and-implementations). The [`backend/chainlit/discord/app.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py) file also ensures that all necessary asynchronous operations are managed efficiently, crucial for maintaining responsiveness in a real-time environment.

### Processing Discord Messages and File Attachments

link

zoom\_in

Incoming Discord messages are processed by first removing any bot mentions using the [`clean_content`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/slack/app.py#L192) function within [`backend/chainlit/discord/app.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py). The cleaned message content is then converted into a Chainlit [`Message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/message.py#L199) object. File attachments included in Discord messages are handled by downloading them using [`download_discord_file`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L174) and [`download_discord_files`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L183) from [`backend/chainlit/discord/app.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py). These downloaded files are then persisted within the Chainlit session and transformed into Chainlit [`Element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L70) objects, which can be displayed in the Chainlit UI. This process ensures that rich content and context from Discord interactions are accurately represented within the Chainlit application. For more details on the context surrounding these operations, refer to [Discord Integration Core Functionality and Context Management](https://codewiki.google/github.com/chainlit/chainlit#external-service-integrations-discord-integration-core-functionality-and-context-management).

### Feedback Mechanisms and Interactive Elements in Discord

link

zoom\_in

Interactive feedback mechanisms within Discord allow users to provide immediate input on bot responses, which is then recorded for analysis. This is primarily facilitated by the [`FeedbackView`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L29) class in [`backend/chainlit/discord/app.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py), which renders "thumbs up" and "thumbs down" buttons on bot messages. When a user interacts with these buttons, the corresponding feedback (positive or negative) is captured and persisted through the Chainlit data layer. This integration ensures that user sentiment regarding the AI assistant's performance in Discord can be logged and utilized. The [`DiscordEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L59) in [`backend/chainlit/discord/app.py`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py) is responsible for attaching these [`FeedbackView`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L29) components to [`assistant_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L25) steps before they are sent to Discord. The feedback data itself is then managed through the [Unified Data Layer Interface and Implementations](https://codewiki.google/github.com/chainlit/chainlit#data-persistence-and-storage-unified-data-layer-interface-and-implementations).

### Real-time Step Emission and Updates to Discord

link

zoom\_in

The [`DiscordEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L59) plays a central role in facilitating real-time communication between the Chainlit backend and Discord. This component is responsible for translating Chainlit's internal representations of elements and steps into messages that can be displayed within Discord channels.

When Chainlit generates an [`Element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/element.py#L70) object, such as a file attachment, the [`DiscordEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L59) utilizes its [`send_element`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L61) method to transmit this as a Discord file message. This involves checking if the file has already been persisted or, if it's a new URL-based element, downloading its content. Similarly, for [`StepDict`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L45) objects, which represent conversational messages, the [`send_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L77) method handles their dispatch to Discord. A key feature of this process is the dynamic attachment of interactive feedback views (e.g., "thumbs up" and "thumbs down" buttons) to assistant messages when feedback is enabled. This allows users to provide direct feedback on the AI's responses, which is then recorded through Chainlit's data layer. While [`update_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L81) exists to modify existing messages, for [`assistant_message`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/step.py#L25) types, it currently defaults to the [`send_step`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/emitter.py#L77) behavior, implying that updates often result in a new message or a re-rendering of the previous one with modifications.

The overall context for this real-time interaction is managed by [`init_discord_context`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L133), which establishes a [`ChainlitContext`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/context.py#L23) for each Discord session, configuring the [`DiscordEmitter`](https://github.com/chainlit/chainlit/blob/b2af84ccd13c0b12c62e226a9e882ed0d96ac1b8/backend/chainlit/discord/app.py#L59) and linking Discord-specific information to the user's session. More details on the broader Discord integration can be found in [Discord Integration Core Functionality and Context Management](https://codewiki.google/github.com/chainlit/chainlit#external-service-integrations-discord-integration-core-functionality-and-context-management).
